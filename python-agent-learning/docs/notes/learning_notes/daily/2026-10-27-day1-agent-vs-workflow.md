# 2026-10-27 Day 1：Agent vs Workflow 边界判断

## 今日主题

页面需求分析为什么需要 Agent，哪些部分只是普通 Workflow。

## 核心结论

先假设用 Workflow，只有 Workflow 解决不了的不确定性，才引入 Agent。

一句话：

> 确定性流程用 Workflow，不确定判断用 Agent；企业落地通常是 Workflow 管边界，Agent 处理复杂判断。

## 普通 Workflow 更适合什么

Workflow 适合流程固定、分支明确、失败可枚举的任务。

典型特征：

- 步骤固定。
- 输入结构稳定。
- 工具调用顺序可预设。
- 每个分支条件明确。
- 失败类型基本可枚举。
- 对审计、权限、合规要求强。

企业例子：

- 表单提交：校验字段 -> 调接口 -> 展示结果。
- 审批流：提交 -> 审批 -> 通过/驳回 -> 通知。
- 支付链路：下单 -> 锁库存 -> 支付 -> 回调 -> 对账。
- 批量操作：选择记录 -> 二次确认 -> 调接口 -> 展示成功/失败明细。

这些场景不应该为了“智能”强行 Agent 化。固定流程越多，越应该用 Workflow 保证稳定性。

## 没有 Agent 以前怎么处理

没有 Agent 以前，企业不是不处理这些问题，而是主要靠人和固定流程处理。

常见方式：

- 靠产品、研发、测试评审：
  - PRD 是否完整，主要靠评审会发现。
  - 权限、异常态、空状态、边界条件，靠有经验的人追问。
  - 问题是强依赖个人经验，容易漏，也容易在多人协作中丢上下文。
- 靠模板和 checklist：
  - PRD 模板要求写清楚背景、目标、角色、流程、异常。
  - 测试 checklist 要求覆盖 loading、empty、error、permission。
  - 问题是模板只能提醒，不能判断内容是否真的合理。
- 靠固定规则系统：
  - 表单校验、审批流、状态机、权限矩阵都属于规则系统。
  - 适合稳定、明确、可枚举的业务。
  - 问题是遇到自然语言需求、模糊描述、跨文档信息时就不够灵活。
- 靠人工查资料和对齐：
  - 研发去翻接口文档、历史需求、设计稿、会议纪要。
  - 测试去问产品补边界条件。
  - 项目经理在群里反复确认。
  - 问题是耗时，而且很多判断无法沉淀成自动化能力。
- 靠传统自动化脚本：
  - 脚本能跑固定检查，例如字段是否存在、接口是否返回、单测是否通过。
  - 问题是脚本只会检查明确规则，不会理解“这段需求是不是缺了权限说明”。

所以 Agent 不是替代所有流程，而是补上过去最依赖人工经验的部分：

```text
过去：人读需求 -> 人发现问题 -> 人追问 -> 人整理结论
现在：Agent 先分析 -> 标出缺口和风险 -> 人确认关键判断
```

企业更现实的变化是：

- Workflow 继续负责稳定流程。
- checklist 继续负责质量底线。
- 规则系统继续负责确定性校验。
- Agent 负责模糊需求理解、缺口发现、跨资料归纳和建议生成。

## Agent 更适合什么

Agent 适合目标明确但路径不确定的任务。

典型特征：

- 输入是自然语言、文档、会议纪要、PRD 等非结构化内容。
- 用户需求可能缺字段、缺上下文、前后不一致。
- 需要根据中间结果决定下一步。
- 需要动态选择工具。
- 需要在执行后观察结果并修正策略。
- 输出不是单个结果，而是一组分析、计划、风险和建议。

企业例子：

- 分析 PRD，识别缺失需求和风险。
- 阅读多份文档后生成调研结论。
- 根据故障现象自动定位可能原因。
- 根据用户问题决定查知识库、查接口、查日志还是追问。
- 根据执行结果继续调整搜索、检索或代码修改策略。

更多企业例子：

- 需求评审助手：
  - 输入：PRD、设计稿说明、接口草案。
  - Agent 判断：哪些规则没写清楚、哪些状态遗漏、哪些接口字段有风险。
  - 价值：提前发现权限、异常态、边界条件和测试盲区。
- 前端开发助手：
  - 输入：页面需求或设计稿描述。
  - Agent 判断：应该拆哪些组件、哪些状态需要单独管理、哪些交互要二次确认。
  - 价值：把模糊需求转成可开发任务。
- 代码变更分析助手：
  - 输入：一次 MR diff。
  - Agent 判断：这次改动影响哪些模块、可能引入哪些回归、需要补哪些测试。
  - 价值：辅助 code review，而不是只做格式检查。
- 线上问题排查助手：
  - 输入：用户反馈、错误日志、监控指标。
  - Agent 判断：先查日志还是查接口，是否需要对比版本，是否可能是配置问题。
  - 价值：把排查路径从“人凭经验找”变成“系统按证据推进”。
- 客服工单分诊助手：
  - 输入：用户自然语言投诉。
  - Agent 判断：是账号问题、支付问题、权限问题还是产品使用问题，是否需要追问。
  - 价值：提升分流准确率，减少人工来回转单。
- 数据分析助手：
  - 输入：业务方的问题，例如“为什么本周转化率下降”。
  - Agent 判断：先查哪个指标、按哪个维度拆解、是否需要看活动、渠道、版本或人群。
  - 价值：把开放式分析问题拆成可执行的数据查询路径。
- 知识库问答助手：
  - 输入：员工问题。
  - Agent 判断：先检索制度文档、项目文档还是历史工单，答案是否需要引用来源。
  - 价值：不是简单问答，而是带检索、判断、引用和置信度控制。
- 自动化测试助手：
  - 输入：页面需求或用户路径。
  - Agent 判断：哪些路径是主流程、哪些是异常流、哪些断言必须覆盖。
  - 价值：从需求中补出更完整的测试场景。
- 安全或权限检查助手：
  - 输入：功能说明、接口设计、权限矩阵。
  - Agent 判断：是否存在越权、敏感信息暴露、缺少二次确认或审计记录。
  - 价值：在需求和设计阶段提前发现风险。
- 运营活动配置助手：
  - 输入：活动目标、规则描述、历史活动结果。
  - Agent 判断：配置项是否完整、规则是否冲突、是否需要灰度和兜底。
  - 价值：降低活动配置错误和规则遗漏。

## 页面需求分析项目里的边界

当前 `02_requirement_analyzer.py` 更像结构化输出 Workflow。

原因：

- 输入固定是一段页面需求。
- 输出固定是 `RequirementAnalysis`。
- 没有工具调用。
- 没有多步循环。
- 没有根据中间结果调整策略。

当前最小流程：

```text
自然语言页面需求
  -> Pydantic schema
  -> 模型结构化输出
  -> JSON 结果
```

## 为什么后续仍然需要 Agent

企业里的真实页面需求通常不完整。

常见问题：

- PRD 没写权限规则。
- 设计稿没写空状态。
- 接口依赖不清楚。
- 批量操作失败策略没定义。
- 不同角色按钮差异没描述。
- 测试点容易漏掉 loading、empty、error、permission。

这些不是固定字段提取能稳定解决的，需要 Agent 做：

```text
识别缺失信息
  -> 拆组件
  -> 推断状态
  -> 生成风险
  -> 必要时追问或调用工具
  -> 修正输出
```

## 更好的企业落地方式

不要把整个系统都做成 Agent。

更合理的是：

```text
外层 Workflow：控制流程、权限、审计、输出格式
内层 Agent：处理不确定的判断、拆解、检索、修正
```

例如页面需求分析 Agent：

- Workflow 固定步骤：
  - 接收需求。
  - 校验输入。
  - 调用分析模块。
  - 输出结构化结果。
  - 保存 trace。
  - 跑 eval。
- Agent 负责不确定判断：
  - 判断需求是否完整。
  - 判断页面类型。
  - 推断组件拆分。
  - 推断状态设计。
  - 识别风险和测试点。

## 面试或复盘表达

可以这样回答：

```text
当前页面需求分析的第一阶段可以用 Workflow 完成，因为它只是把自然语言需求转换成固定 schema 的结构化输出。

但在企业真实业务里，需求往往是不完整、不一致、带隐含约束的。比如权限规则、异常态、接口依赖、批量操作失败策略经常缺失。此时系统不能只按固定流程抽字段，而需要根据输入内容判断缺口、选择分析工具、结合中间结果继续修正输出。

所以更合理的设计是：外层用 Workflow 固定主流程和输出规范，内层用 Agent 处理不确定的分析环节，例如组件拆分、状态推断、风险识别和测试点补全。
```
