## 1. RAG 文档入库前为什么要清洗页眉、页脚、导航和重复段落？

- **分类**：RAG 数据处理
- **难度**：初级
- **考察要点**：数据清洗、模板噪声、重复召回、入库质量
- **参考答案**：
  - 页眉、页脚、网页导航和版权说明通常会在很多页面重复。若直接切分并向量化，它们可能形成大量相似 Chunk，挤占真正有用内容的召回位置和上下文 Token。
  - 入库前应去除模板噪声、空白和明显重复内容，同时保留标题、正文、表格及来源位置等业务信息。
  - 清洗后要抽样检查原文，避免把页码、章节标题或表头等仍有定位和理解价值的信息误删。
- **通俗理解**：这像把一本书复印后，每页都重复印上目录和广告。若不先清理，搜索时会反复找到广告，却把真正回答问题的正文挤到后面。

## 2. RAG 回答中的引用怎样保证能准确定位原文，而不是只显示一个文件名？

- **分类**：RAG 引用溯源
- **难度**：初中级
- **考察要点**：唯一标识、Chunk 来源、引用映射、可验证性
- **参考答案**：
  - 检索结果应携带稳定的 `document_id`、`chunk_id`、版本和页码或段落位置，Prompt 中用来源编号关联这些元数据。
  - 模型只负责在答案中输出来源编号；后端再把编号映射为真实文档链接或定位信息，不能只按可能重名的文件名查找。
  - 返回前还应校验引用编号是否存在、对应 Chunk 是否真的支持答案；文档更新后要保留版本关系，避免引用跳到另一版内容。
- **通俗理解**：文件名像书名，同名书可能有很多本；`document_id` 和 `chunk_id` 更像 ISBN 加页码。用户点击引用时，系统应按唯一编号找到那一版的具体段落，而不是猜是哪份同名文件。

## 3. 压缩 Agent 对话历史时，为什么不能随便删除一条工具调用或工具结果消息？

- **分类**：Agent 上下文管理
- **难度**：中级
- **考察要点**：消息配对、`tool_call_id`、有效消息序列、上下文裁剪
- **参考答案**：
  - 一条带 `tool_calls` 的 assistant 消息与后续 tool 结果通过 `tool_call_id` 配对，模型依靠这组消息知道调用了什么以及得到了什么结果。
  - 若只删其中一边，消息序列可能不符合模型接口要求，或让模型失去观察结果，导致报错、重复调用工具或作出错误判断。
  - 裁剪时应按完整交互单元处理：保留或一起摘要“工具调用 + 对应结果”，并检查多次、并行调用的每个 ID 都能匹配。
- **通俗理解**：工具调用像提出问题，工具结果像对应答案。只留下问题或只留下答案，后面的人就无法还原事情经过，因此整理记录时要把一问一答成组处理。

## 4. MCP Client 从连接 Server 到完成一次工具调用，基础流程是什么？

- **分类**：MCP 基础
- **难度**：初中级
- **考察要点**：能力发现、`tools/list`、模型选工具、`tools/call`
- **参考答案**：
  - Client 先与 Server 建立连接并完成协议版本与能力发现，确认对方是否提供 Tools 等能力；不同 MCP 协议版本由 SDK 封装的握手细节可能不同。
  - Client 通过 `tools/list` 获取工具名称、描述和输入 Schema，把可用工具提供给模型；模型根据用户任务选择工具并生成参数。
  - 应用校验参数后发送 `tools/call`，Server 执行真实能力并返回结果，应用再把结果交给模型继续判断或生成最终答案。
  - MCP 解决的是能力发现和调用协议，不替代模型决策、业务鉴权、参数校验与高风险操作确认。
- **通俗理解**：这像先问服务台“你们能办哪些业务”，拿到业务清单后再选择窗口并提交材料。MCP 规定了查询清单和办理业务的通用说法，但是否有权限办理仍由业务系统判断。

## 5. 初中级 Agent 项目应该怎样建立第一版小型评测集？

- **分类**：Agent 效果评估
- **难度**：初中级
- **考察要点**：代表性样本、预期结果、边界场景、持续回归
- **参考答案**：
  - 第一版不必追求大量样本，可先从真实业务中人工整理一小批代表性问题，覆盖正常任务、缺少参数、工具失败、无答案和安全边界等场景。
  - 每条样本至少保存输入和可检查的预期结果；按任务补充期望工具、关键参数、目标文档或是否应拒答，避免只比较最终文案。
  - Prompt、模型、工具或流程变更后固定回放同一批样本，比较任务成功率、工具调用正确性、答案依据、延迟和成本。
  - 线上新 Badcase 经脱敏和人工确认后再加入评测集，使它逐步覆盖真实用户问题。
- **通俗理解**：这像先做一本小而准的错题册，不需要一开始就收集几千题。每次改 Agent 都用同一批题重考，发现新的典型错误再补进去，才能看出改动究竟是进步还是退步。
