## 1. RAG 检索带有时间、版本或业务类型条件时，为什么通常要做元数据预过滤？

- **分类**：RAG 检索
- **难度**：初中级
- **考察要点**：元数据过滤、预过滤与后过滤、召回完整性
- **参考答案**：
  - 向量相似度只表示语义接近，不能保证文档属于正确租户、版本、时间范围或业务类型，因此这些确定性条件应作为元数据过滤条件。
  - 预过滤是先缩小合法候选集合，再从中做向量检索；后过滤是先取全库 Top-K，再删除不满足条件的结果。
  - 当过滤条件很严格时，后过滤可能把 Top-K 删到只剩很少结果，甚至漏掉候选集合中本来相关的内容。初中级项目通常优先使用向量库支持的预过滤，同时通过实际数据评估召回率和延迟。
- **通俗理解**：这像先限定“2026 年生效的北京地区制度”，再从这些制度里找最相似的条款。若先从全国所有年份里挑 5 条再过滤，很可能 5 条都被删掉，看起来就像知识库没有答案。

## 2. RAG 召回的多个 Chunk 内容重复或前后相邻时，送给大模型前应该怎么处理？

- **分类**：RAG 上下文组装
- **难度**：初中级
- **考察要点**：结果去重、相邻块合并、来源定位、Token 控制
- **参考答案**：
  - 先按 `chunk_id`、内容哈希或标准化文本做精确去重，再对高度相似的重复片段保留相关性更高、版本更新或来源更可靠的一份。
  - 对同一文档中前后相邻且共同构成完整语义的 Chunk，可按原始顺序合并；不要把不同文档或相距很远的片段仅因语义相似就强行拼接。
  - 合并后仍要保留 `doc_id`、原始 Chunk 范围和引用信息，并控制总 Token 预算。必要时只抽取与问题相关的句子，但要防止压缩丢失限定条件、数字和否定词。
- **通俗理解**：检索结果像从一本书里撕出的几张纸，相邻两页可以按页码拼回去，重复复印件只留一份。这样既不给模型重复材料，也不会把不同章节硬拼成一段错误上下文。

## 3. 用户点击“停止生成”时，为什么不能只让前端断开流式连接？

- **分类**：Agent 工程落地
- **难度**：初中级
- **考察要点**：取消信号、Agent Loop、工具执行、状态一致性
- **参考答案**：
  - 前端断流只是不再显示内容，后端 Agent、模型请求或工具可能仍在运行并继续消耗资源，甚至继续执行写入操作。
  - 取消信号应从请求入口传到 Agent Loop、模型调用和工具层；循环在开始下一步前检查信号，支持取消的模型请求和长耗时工具也应尽快终止并释放资源。
  - 已经完成的副作用不能假装撤销，应记录任务为“已取消”以及哪些步骤已经完成；付款、发消息等操作还要查询真实结果，必要时执行明确的补偿流程。
- **通俗理解**：关掉外卖 App 的进度页面，并不会让骑手自动停止配送。真正取消任务要通知整条执行链，还要确认订单是否已经扣款或出餐，不能只把页面藏起来。

## 4. Agent 一边生成答案一边调用工具时，流式接口应该向前端区分哪些事件？

- **分类**：Agent 工程落地
- **难度**：初中级
- **考察要点**：事件类型、工具进度、关联标识、最终状态
- **参考答案**：
  - 不应把所有内容都当作文本 Token。至少要区分回答增量、工具开始、工具完成、步骤或状态更新、最终结果、错误和取消等事件。
  - 每个事件应带稳定的 `run_id`，工具事件还应带 `call_id`，让前端能把开始与结果配对，并在重连或重复事件时正确更新同一个任务。
  - 前端可以展示“正在检索”“已完成查询”等明确进度，但不应直接暴露模型内部推理、敏感工具参数或未完成的 Function Call 参数；只有最终完成事件才能表示任务成功。
- **通俗理解**：这像快递跟踪不能把“运输中、到站、签收”全部当成普通聊天文字。给事件分类型并带上任务编号，页面才知道该更新进度、展示答案，还是提示失败。
