## 1. LLM-as-a-Judge 常见的偏差有哪些？如何证明自动评分可信？

- **分类**：评估
- **难度**：中高级
- **考察要点**：位置偏差、冗长偏差、自我偏好、人工校准、评分稳定性
- **参考答案**：
  - LLM Judge 可能偏爱排在前面的候选、内容更长的回答或与自身风格相似的输出，也可能因评分 Prompt、模型版本和采样产生波动，因此不能把单次评分当成客观真值。
  - 应先定义具体且可观察的 Rubric，并提供经过人工确认的正反例；能用规则验证的格式、引用和业务结果优先使用确定性检查，只把主观质量交给 Judge。
  - 对 Pairwise 评估应交换候选顺序并检查结论是否一致；在一批人工标注样本上计算一致率、分项误差和重复评分稳定性，并定期抽检线上结果。
  - Judge 模型、Prompt 和 Rubric 都要版本化。只有自动评分与目标人群的人工判断达到预设一致性，才能用于回归门禁。
- **通俗理解**：自动评委也会有偏心，例如更喜欢先看到的答案或写得更长的答案。要像培训真人评委一样给它明确评分标准，再用人工样本检查它是否判得稳定、判得符合业务需要。

## 2. 语义缓存与精确匹配缓存有什么区别？哪些场景不能直接使用语义缓存？

- **分类**：性能与缓存
- **难度**：中高级
- **考察要点**：向量相似度、命中阈值、缓存隔离、时效性与副作用
- **参考答案**：
  - 精确匹配缓存只在规范化后的请求键完全一致时命中；语义缓存先将请求向量化，再按相似度阈值复用含义接近问题的历史回答，因此命中率更高，但可能发生错误复用。
  - 缓存键或过滤条件至少要包含租户、权限范围、模型与 Prompt 版本、工具和知识库版本，以及会影响答案的业务参数；同时设置 TTL，并在数据或权限变化时主动失效。
  - 涉及用户私有数据、实时价格与库存、高风险决策、随机创作或会产生副作用的请求，不应仅凭语义相似就返回旧结果。相似阈值必须通过真实查询集评估误命中率，不能凭经验拍定。
  - 应监控命中率、错误命中率、节省的 Token、延迟和陈旧答案比例；不确定时宁可回源生成。
- **通俗理解**：精确缓存像只有问题一字不差才复用答案，语义缓存则会把“北京天气怎样”和“北京今天天气如何”视为同类。它更容易命中，但如果把不同用户的余额查询也当成同一个问题，复用结果就会出严重错误。

## 3. 推测解码为什么能加速 LLM 生成？什么情况下反而收益很低？

- **分类**：LLM 推理性能
- **难度**：高级
- **考察要点**：Draft Model、并行验证、接受率、分布一致性、延迟收益
- **参考答案**：
  - 推测解码先让更快的 Draft Model 一次提出多个候选 Token，再由目标模型在一次前向计算中并行验证；被接受的连续候选越多，目标模型串行解码的轮数就越少。
  - 使用正确的接受与修正采样算法时，可以在不改变目标模型输出分布的前提下加速，而不是简单采用小模型的答案。
  - 收益取决于 Draft 与目标模型的一致程度、Draft 成本、验证批次和硬件利用率。候选接受率低、Draft 本身较慢、输出很短，或目标服务已通过大批处理充分占满 GPU 时，额外草拟与验证开销可能抵消收益。
  - 评估时应比较端到端延迟、每个目标模型调用接受的 Token 数、吞吐和输出质量，不能只看理论减少了多少解码步。
- **通俗理解**：这像让助手先草拟后面几句话，专家一次检查一整段；草稿大多正确时，就不用专家逐字写。如果助手经常猜错或写草稿本身很慢，专家不断退回重写，反而省不了时间。

## 4. 升级 Embedding 模型时，为什么不能把新旧向量直接混在同一个索引里？

- **分类**：RAG 生产工程
- **难度**：高级
- **考察要点**：向量空间、维度兼容、双索引迁移、离线与在线验证
- **参考答案**：
  - 不同 Embedding 模型即使输出维度相同，也通常处于不同的表示空间，向量距离不可直接比较；维度不同则连索引结构都可能不兼容。查询用新模型、文档仍是旧向量会导致相关性失真。
  - 应为文档记录 Embedding 模型、维度、归一化方式和内容版本，并建立独立的新索引全量或增量回填，不能原地混写。
  - 迁移前用固定检索集比较 Recall@K、nDCG、下游答案质量、索引大小、延迟和成本；上线时通过影子查询或小流量对比新旧索引，验证后再切换别名或路由。
  - 迁移期间要保证更新和删除同时写入两套索引，切换后保留可回滚窗口，最后再下线旧索引。
- **通俗理解**：不同 Embedding 模型像两套地图坐标，北京在两张地图上的数字不能直接拿来算距离。正确做法是用新坐标重建一张完整地图，经过对照测试后再把查询入口切过去。

## 5. Agent 需要执行模型生成的代码时，沙箱应该限制哪些能力？

- **分类**：Agent 安全
- **难度**：高级
- **考察要点**：隔离边界、最小权限、网络与文件系统、资源限制、凭证保护
- **参考答案**：
  - 模型生成的代码和依赖都应视为不可信输入，不能直接在 Agent 主进程或宿主机执行。每次任务应运行在隔离环境中，并使用非特权用户、只读基础文件系统和最小挂载目录。
  - 默认关闭网络，只按域名、协议和端口放行必要出口；不得把宿主环境变量、云元数据地址、Docker Socket、SSH Key 或长期凭证注入沙箱。
  - 必须限制 CPU、内存、进程数、磁盘、输出大小和执行时间，禁用不必要的系统调用与特权能力，并在结束后销毁临时环境。
  - 普通容器共享宿主内核，风险较高时可使用 gVisor、MicroVM 等更强隔离；同时记录代码摘要、镜像版本、资源使用和网络访问，支持审计与复现。
- **通俗理解**：让 Agent 跑代码像让陌生人在临时工作间做实验，不能把公司的钥匙和整栋楼的门禁都交给他。工作间要限制能访问的文件、网络和用电量，任务结束后还要彻底清理。
- **来源**：[cite:10](#source-10) [cite:11](#source-11)

## 6. Prompt、模型或 Agent 工作流变更应如何灰度发布和快速回滚？

- **分类**：生产工程
- **难度**：高级
- **考察要点**：版本化、离线回归、影子流量、金丝雀、质量与成本门禁
- **参考答案**：
  - Prompt、模型、工具 Schema、检索配置和工作流都应有不可变版本，并让每次 Trace 记录实际版本；回滚必须能够恢复整套兼容配置，而不是只回退其中一个模型名称。
  - 发布前先运行固定回归集和安全攻击集。影子流量可以把真实请求复制给新版本但不向用户返回结果，适合比较输出与性能；金丝雀发布则让少量真实流量真正使用新版本，用于验证端到端行为。
  - 灰度阶段要按版本分别观察任务成功率、严重错误率、安全违规、P95 延迟、Token 和单任务成本，并与同期控制组比较，避免把流量时段差异误判为版本效果。
  - 一旦越过预设门槛应自动停止扩量并切回稳定版本；有副作用的工具调用不能在影子链路真实执行，或必须使用隔离环境和幂等保护。
- **通俗理解**：这像餐厅换菜单，先在内部试菜，再让少量顾客尝试并和旧菜单同期比较。若投诉、出餐时间或成本明显变差，就应立刻切回完整的旧方案，而不是临时猜哪一种调料出了问题。

## 7. MCP 中 Tools、Resources 和 Prompts 分别适合暴露什么能力？

- **分类**：MCP
- **难度**：中级
- **考察要点**：能力语义、控制主体、URI 与 Schema、副作用边界
- **参考答案**：
  - `Tools` 表示可执行操作，由模型根据上下文选择调用，使用输入 Schema 描述参数，可能查询系统或产生副作用，因此需要参数校验、授权和高风险确认。
  - `Resources` 表示可读取的上下文数据，例如文件、数据库 Schema 或业务资料，以 URI 标识，主要由应用选择、读取或订阅变化；读取资源不应伪装成具有副作用的操作。
  - `Prompts` 是服务端提供的可复用消息模板和参数，通常由用户显式选择，例如斜杠命令；它负责组织交互方式，不等同于执行工具。
  - 设计时应按语义选择能力类型，而不是把所有内容都包装为 Tool。Host 仍负责决定哪些能力进入上下文、哪些调用需要确认，以及用户是否有权访问。
- **通俗理解**：Tool 像能执行动作的按钮，Resource 像可以打开阅读的资料，Prompt 像预先写好的办事模板。把三者分清后，用户和模型才知道是在“做事”“读资料”还是“套用流程”。
- **来源**：[cite:13](#source-13) [cite:14](#source-14) [cite:15](#source-15)

## 8. LangGraph 的 Send API 适合解决什么问题？它与固定并行边有什么区别？

- **分类**：LangGraph
- **难度**：中高级
- **考察要点**：动态 Fan-out、Map-Reduce、局部输入、结果归并、并发上限
- **参考答案**：
  - 固定并行边适合编译图时已经知道的并行节点；`Send` 允许路由函数在运行时根据当前数据动态创建多个目标节点调用，例如按文档列表生成数量不确定的摘要任务。
  - 每个 `Send` 可以携带该 Worker 所需的局部状态，Worker 完成后再通过父图 State 中定义的 Reducer 汇总结果，形成 Map-Reduce。
  - 动态 Fan-out 仍要限制最大 Worker 数和在途并发，并分别处理超时、部分失败、重试与结果顺序；否则一次超大输入会放大模型调用数量、成本和下游压力。
  - 若任务数量固定或存在严格前后依赖，普通边或顺序节点更清晰，不应为使用动态能力而增加复杂度。
- **通俗理解**：固定并行像提前安排好三个人同时工作，`Send` 则像收到一摞文件后，按实际文件数量临时派发任务。派出去的结果还要有明确的汇总规则，并限制一次最多派多少人。
- **来源**：[cite:16](#source-16) [cite:17](#source-17)

## 9. Prompt、RAG、LoRA 和全量微调分别适合解决什么问题？

- **分类**：模型适配
- **难度**：中高级
- **考察要点**：知识与行为边界、参数高效微调、更新成本、选型顺序
- **参考答案**：
  - Prompt 适合明确任务、输出格式和少量示例；RAG 适合引入频繁变化、需要引用或受权限控制的外部知识，两者都不修改模型参数。
  - LoRA 冻结基础模型，只训练插入的低秩参数，适合用较低训练和存储成本调整稳定的行为、风格或领域模式；它仍需要高质量训练数据和独立评测。
  - 全量微调更新全部参数，资源和版本维护成本最高，通常只在需要深度改变模型能力且数据、算力与收益足以支撑时考虑。
  - 不应使用微调记忆频繁变化的事实，也不能期待 RAG 自动修复模型不遵循格式或工具策略的问题。实践中通常先建立评测集，再从 Prompt 和 RAG 开始，证明确有稳定行为缺口后再考虑 LoRA 或全量微调。
- **通俗理解**：Prompt 像当场说明任务，RAG 像给员工一本最新资料，LoRA 像用较小成本做专项培训，全量微调则像重新系统培养。资料天天变化时应更新资料库，而不是每次都重新培训员工。

## 10. PagedAttention 解决了什么问题？为什么它能提高 LLM 服务吞吐？

- **分类**：LLM 服务性能
- **难度**：高级
- **考察要点**：KV Cache 碎片、分页管理、批处理容量、吞吐与延迟
- **参考答案**：
  - 每个请求的 KV Cache 会随生成长度动态增长，若为最大长度预留连续显存，会产生内部浪费；不同请求频繁进入和结束也会造成外部碎片，限制可同时批处理的请求数。
  - PagedAttention 借鉴操作系统分页，把每个序列的 KV Cache 拆成固定大小块，通过映射表组织逻辑连续但物理上可分散的块，从而减少预留和碎片浪费。
  - 更高的 KV Cache 利用率允许同一显存容纳更多并发序列，也便于不同请求共享前缀块，因此可提升批处理规模和总体吞吐。
  - 它优化的是显存管理而非模型计算量本身。块管理仍有开销，实际收益要结合序列长度分布、并发、TTFT、每 Token 延迟和显存占用共同测试。
- **通俗理解**：传统方式像每位乘客都提前占一整排座位，哪怕只坐一个位置也不能给别人用。PagedAttention 把座位按小块灵活分配，空位更少，同一辆车就能同时服务更多乘客。
- **来源**：[cite:7](#source-7) [cite:19](#source-19)
