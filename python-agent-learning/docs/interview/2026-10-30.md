## 1. 工具的名称和描述为什么会影响 Agent 能否选对工具？应该怎么写？

- **分类**：工具设计
- **难度**：初级
- **考察要点**：工具选择、名称、描述、职责边界
- **参考答案**：
  - 模型通常根据工具的名称、描述和参数 Schema 判断“什么时候调用哪个工具”，描述含糊或多个工具职责重叠时就容易选错。
  - 名称应体现动作和对象，例如 `search_orders` 比 `query` 更明确；描述要说明适用场景、不适用场景、输入含义和返回内容。
  - 相近工具要写清边界，例如一个查订单详情、一个查订单列表，不能只写成两个“查询订单”。
  - 应使用真实任务集统计选错工具、漏调工具和参数错误，再根据 Trace 改进描述，而不是只凭感觉修改。
- **通俗理解**：工具说明像抽屉标签，标签都写“资料”时很容易拿错。写清“查订单列表”和“查单个订单详情”，Agent 才知道该开哪个抽屉。

## 2. 工具执行结果为什么要带回对应的 `call_id`？

- **分类**：Tool Calling
- **难度**：初级
- **考察要点**：调用关联、工具结果、多次调用、消息协议
- **参考答案**：
  - `call_id` 用于把某个工具结果与模型发出的那一次工具调用对应起来，让模型知道“这份结果回答的是哪次请求”。
  - 一轮中可能有多个工具调用，甚至同一个工具被调用多次；只返回结果文本而不关联调用，容易造成结果错配。
  - 程序应保存模型返回的工具调用信息，执行工具后用相同的 `call_id` 回传结果，再让模型继续生成答案或决定下一步。
  - `call_id` 解决的是协议关联问题，不代表结果可信；程序仍需校验工具是否成功以及返回格式是否正确。
- **通俗理解**：这像餐厅取餐号，同桌一次点了多份餐，每份餐都要对应自己的号码。没有号码，服务员就可能把结果送错请求。

## 3. `developer/system`、`user`、`assistant` 和 `tool` 消息分别有什么作用？

- **分类**：Prompt 基础
- **难度**：初级
- **考察要点**：消息角色、指令优先级、对话历史、工具结果
- **参考答案**：
  - `developer/system` 消息放应用规则、角色和业务约束，优先级通常高于普通用户请求。
  - `user` 消息表示用户输入；`assistant` 消息保存模型先前的回答或工具调用请求，用于维持对话连续性。
  - `tool` 消息用于把程序实际执行工具后的结果返回给模型，并关联对应的工具调用。
  - 不应把用户输入直接拼进高优先级指令，也不要把工具结果伪装成系统规则，否则会混淆可信边界。
- **通俗理解**：高优先级消息像公司的工作制度，用户消息像客户需求，assistant 是员工之前的处理记录，tool 是业务系统返回的查询结果。把客户原话写进公司制度，会让规则和需求混在一起。
- **来源**：[cite:3](#source-3) [cite:5](#source-5)

## 4. LangGraph 中的 Node、Edge 和 Conditional Edge 分别做什么？

- **分类**：LangGraph
- **难度**：初级
- **考察要点**：节点、边、条件路由、状态流转
- **参考答案**：
  - Node 是一个处理步骤，读取当前 State，执行模型、工具或普通 Python 逻辑，并返回状态更新。
  - Edge 定义固定的下一步，例如解析完成后总是进入检索节点。
  - Conditional Edge 根据当前 State 或路由函数的结果选择下一节点，例如参数完整则调用工具，缺少参数则进入澄清节点。
  - 图的入口从 `START` 开始，满足结束条件后进入 `END`；关键路由结果应是明确、可校验的有限取值。
- **通俗理解**：Node 像地铁站，Edge 像固定线路，Conditional Edge 像根据目的地选择不同换乘方向。State 就是乘客随身携带的行程信息。
- **来源**：[cite:1](#source-1) [cite:6](#source-6)

## 5. Agent 的 State 和 Memory 有什么区别？

- **分类**：状态与记忆
- **难度**：初中级
- **考察要点**：运行状态、短期记忆、长期记忆、生命周期
- **参考答案**：
  - State 是当前任务执行时的工作数据，例如当前步骤、工具结果、错误和剩余计划，主要服务于流程推进。
  - Memory 是需要在后续步骤或会话中再次使用的信息；短期记忆通常限于同一线程，长期记忆可跨会话保存用户偏好或稳定事实。
  - Memory 可以作为 State 的一部分被读取，但不是所有 State 都值得长期保存，例如临时重试次数通常不应成为长期记忆。
  - 设计时应先明确生命周期和读取场景，只保存后续确实需要的信息，避免把完整日志都当成记忆。
- **通俗理解**：State 像做菜时台面上的当前步骤和剩余食材，Memory 像菜谱和家人的口味偏好。炒到第几步很快会过期，但“少放辣”可能下次还要用。
- **来源**：[cite:1](#source-1) [cite:7](#source-7)

## 6. 为什么 RAG 建库和查询必须使用兼容的 Embedding 模型与配置？

- **分类**：RAG Embedding
- **难度**：初中级
- **考察要点**：向量空间、维度、建库、查询
- **参考答案**：
  - 向量检索要比较查询向量和文档向量的相似度，因此两者必须处于同一个可比较的向量空间。
  - 不同模型的向量维度、训练目标和空间分布可能不同；即使维度相同，也不代表向量可以直接比较。
  - 建库和查询应使用同一模型版本以及一致的归一化、查询前缀或 `encode_query`、`encode_document` 规则。
  - 更换模型或关键编码配置后，通常要重新生成文档向量并重建索引，再用业务问题集验证召回效果。
- **通俗理解**：这像用两套不同坐标系标记地点，数字都有经纬度的样子，却不能直接计算距离。建库和查询使用同一套坐标规则，才能找到真正接近的内容。
- **来源**：[cite:8](#source-8) [cite:9](#source-9) [cite:10](#source-10)

## 7. 初中级项目应该怎样选择和验证 Embedding 模型？

- **分类**：RAG Embedding
- **难度**：中级
- **考察要点**：语言与领域、输入长度、部署约束、业务评测
- **参考答案**：
  - 先看业务语言和领域是否匹配，再检查最大输入长度、向量维度、调用成本、延迟、是否需要本地部署及数据合规要求。
  - 通用排行榜只能用于初筛，不能直接证明模型适合自己的客服、法律或产品文档。
  - 应准备一小批“问题 + 正确 Chunk”样本，让候选模型在相同切分和检索配置下比较 Hit@K、Recall@K 等指标。
  - 最终还要结合答案质量、存储成本和响应时间选型，而不是只选择向量维度最高或榜单分数最高的模型。
- **通俗理解**：选 Embedding 模型像给业务招聘翻译，证书分数高不等于熟悉你的行业术语。要拿真实业务问题试译，再比较效果、速度和成本。
- **来源**：[cite:2](#source-2) [cite:9](#source-9) [cite:10](#source-10)

## 8. RAG 检索到 Chunk 后，应该怎样组装成给大模型的 Prompt？

- **分类**：RAG 生成
- **难度**：初中级
- **考察要点**：上下文组装、来源编号、回答边界、拒答
- **参考答案**：
  - Prompt 应同时包含任务规则、用户原始问题和筛选后的参考 Chunk，并用清晰分隔符或编号区分不同来源。
  - 要明确要求模型优先依据参考资料回答，资料不足时说明无法确认，不能为了完整而自行补全事实。
  - 每个 Chunk 应保留来源编号、文档名或页码，便于答案引用和后续核验；重复或低相关片段应在组装前去掉。
  - 参考资料属于数据而不是高优先级指令，不能让文档中的命令覆盖应用规则。
- **通俗理解**：这像开卷考试，先把相关页按编号放到桌上，再要求只根据这些页作答并标出出处。书页里即使写着“忽略监考规则”，它也只是资料内容，不是新的考试规则。
- **来源**：[cite:1](#source-1) [cite:8](#source-8) [cite:11](#source-11)
