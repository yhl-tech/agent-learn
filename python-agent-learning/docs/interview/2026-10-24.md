## 1. Temperature、Top-p 和 Top-k 分别如何影响模型输出？低 Temperature 是否等于确定性？

- **分类**：LLM 基础
- **难度**：初级
- **考察要点**：采样分布、候选集截断、可复现性边界
- **参考答案**：
  - `Temperature` 调整概率分布的平坦程度，值越高通常越随机；`Top-p` 只从累计概率达到阈值的最小候选集合中采样；`Top-k` 只保留概率最高的 k 个候选。
  - 一般不要同时大幅调整多个采样参数，否则交互效果难以预测；应通过任务评测选择配置，而不是套用固定值。
  - 低 Temperature 只会降低随机性，不保证完全确定。并发执行、模型版本、服务端实现和同概率候选等因素仍可能造成差异，关键流程应依赖结构化校验与业务规则，而不是假设模型输出可复现。
- **通俗理解**：模型每次都像从候选词中抽签，Temperature 控制抽签有多大胆，Top-p 和 Top-k 控制哪些候选有资格进入抽签箱。把 Temperature 调低只是让它更常选热门答案，并不等于每次结果都一模一样。

## 2. JSON Mode、Structured Outputs 和业务校验有什么区别？

- **分类**：结构化输出
- **难度**：中级
- **考察要点**：语法有效性、Schema 约束、语义与业务规则
- **参考答案**：
  - JSON Mode 主要保证输出是合法 JSON，但不保证字段、类型和必填项符合指定 Schema；Structured Outputs 通过 JSON Schema 或严格工具参数约束输出结构。
  - Schema 正确不代表业务语义正确，例如日期可能格式合法但早于允许范围，订单号也可能结构正确但不存在。因此仍要在应用侧使用 Pydantic 等工具解析，并校验枚举、范围、权限和资源状态。
  - 应显式处理拒答、截断、解析失败和业务校验失败；只有可恢复错误才进行有上限的重试，不能把模型输出直接交给高风险下游系统。
- **通俗理解**：JSON Mode 像保证表格能打开，Structured Outputs 像保证列名和类型都正确。即使表格格式完全正确，里面的订单号也可能是假的，所以程序还要再查真实业务数据。

## 3. Python Agent 服务为什么常用 asyncio？怎样避免同步工具阻塞整个服务？

- **分类**：Python Agent
- **难度**：中级
- **考察要点**：I/O 并发、事件循环、阻塞调用、取消与超时
- **参考答案**：
  - LLM、数据库和外部工具调用大多是 I/O 等待，`asyncio` 可以让单个线程在等待期间处理其他请求；相互独立的调用可通过 `TaskGroup` 或 `gather` 并发执行。
  - `async def` 不会自动把内部代码变成非阻塞。同步 HTTP、文件操作或耗时 SDK 会卡住事件循环，应优先使用异步客户端；无法替换的阻塞 I/O 可用 `asyncio.to_thread()` 或执行器隔离。
  - 每个外部调用都应设置超时，并正确传播取消信号；CPU 密集任务更适合进程池或独立任务队列，而不是放在线程中长期占用资源。
- **通俗理解**：事件循环像一个服务员，可以在一道菜烹饪时先照顾其他桌；同步阻塞代码却会让服务员站在厨房门口一直等。把这类工作交给线程或独立进程，其他请求才不会一起被卡住。

## 4. RAG 的 Chunk Size 和 Overlap 应该如何选择？为什么不存在通用最佳值？

- **分类**：RAG
- **难度**：中级
- **考察要点**：语义边界、检索粒度、上下文完整性、实验评估
- **参考答案**：
  - Chunk 太小容易丢失上下文，太大则会混入无关信息、降低检索精度并增加输入成本；Overlap 能缓解边界信息断裂，但会扩大索引并产生重复结果。
  - 应优先沿标题、段落、表格、代码函数或对话轮次等自然边界切分，并保留父文档、章节、页码等元数据；表格和代码不应简单按固定字符数截断。
  - 初始值只是实验起点，最终应在真实问题集上比较 Recall@K、排序质量、答案正确率、延迟和成本，再根据语料类型分别配置。
- **通俗理解**：切文档像把一本书拆成便于查找的卡片，卡片太小会看不懂前因后果，太大又很难快速找到重点。合理做法是尽量按章节和完整段落切，再用真实问题测试哪种大小最容易找到答案。

## 5. 为什么 RAG 评估要把检索和生成分开？常用指标分别是什么？

- **分类**：RAG 评估
- **难度**：中高级
- **考察要点**：故障归因、检索指标、生成指标、端到端指标
- **参考答案**：
  - 最终答案错误可能是没有检索到正确文档，也可能是文档正确但模型理解或生成错误；只看端到端答案无法定位应修复检索器还是生成器。
  - 检索层可用 Hit Rate、Recall@K、MRR、nDCG 和文档相关性；生成层关注正确性、答案相关性、完整性和对检索证据的 Groundedness。
  - 最后还要评估端到端任务成功率、引用正确性、延迟和成本。LLM-as-Judge 适合评估难以规则化的质量，但应使用明确评分标准并以人工标注样本校准。
- **通俗理解**：RAG 像开卷考试，答错可能是没翻到正确页，也可能是翻到了却理解错了。把“找资料”和“写答案”分开评分，才能知道该换检索方法还是改生成提示。

## 6. 向量检索中 Cosine、Dot Product 和 Euclidean Distance 应如何选择？

- **分类**：向量检索
- **难度**：中高级
- **考察要点**：方向与模长、归一化、模型兼容性、索引配置
- **参考答案**：
  - Cosine 关注向量方向，弱化模长影响；Dot Product 同时受方向和模长影响；Euclidean Distance 直接衡量空间距离。
  - 对单位归一化向量，Cosine 与 Dot Product 的排序等价，Dot Product 往往更易优化。若向量未归一化，二者可能给出不同排序，不能随意切换。
  - 应遵循 Embedding 模型推荐的距离函数，并保证建库和查询使用同一模型、同一维度和同一归一化方式；最终通过真实检索集比较 Recall@K 和延迟。
- **通俗理解**：比较向量像比较两支箭，Cosine 主要看方向是否一致，Euclidean 看箭头之间相隔多远，Dot Product 还会考虑箭有多长。先把箭都变成一样长后，Cosine 和 Dot Product 通常会排出相同顺序。

## 7. Prompt Caching 的工作原理是什么？哪些情况下不会带来收益？

- **分类**：性能与成本
- **难度**：中级
- **考察要点**：前缀匹配、静态内容布局、缓存命中率、写入成本
- **参考答案**：
  - Prompt Caching 复用已经处理过的相同前缀，减少重复 Prefill 的延迟和输入成本；工具定义、系统指令、固定背景和示例应放在前面，动态内容放在后面。
  - 前缀在缓存点之前发生变化会导致后续缓存失效，因此时间戳、随机 ID 和每次变化的用户内容不应放进希望复用的静态前缀。
  - 短 Prompt、低重复率、超过 TTL 才复用或频繁变更工具定义时收益有限，缓存写入本身还可能更贵。生产环境应观察缓存读写 Token、命中率、TTFT 和总成本。
- **通俗理解**：Prompt Caching 像把一本固定的操作手册提前读好，下次只读新增的一页。若每次都改手册开头，之前的阅读记录就用不上，反而多做了一次缓存写入。
- **来源**：[cite:13](#source-13) [cite:6](#source-6) [cite:9](#source-9)

## 8. Streaming 为什么主要改善感知延迟，而不一定降低总延迟？

- **分类**：性能与用户体验
- **难度**：中级
- **考察要点**：TTFT、端到端延迟、关键路径、并行化
- **参考答案**：
  - Streaming 让客户端在完整回答生成前收到首批 Token，因此主要改善 Time to First Token 和用户感知等待时间；模型仍要生成完整输出，总完成时间可能基本不变。
  - 优化时应分别测量排队时间、TTFT、工具调用耗时、每秒输出 Token 和端到端延迟，不能只用一个平均值描述性能。
  - 真正缩短总延迟通常需要减少输入和输出 Token、选择更合适的模型、缓存稳定前缀，并行执行无依赖的工具调用，以及消除不必要的 Agent 步骤。
- **通俗理解**：Streaming 像餐厅先上凉菜，客人很快就能开始吃，但整桌菜做完的时间未必变短。要真正提前结束，还得减少菜量、并行做菜或简化步骤。
- **来源**：[cite:14](#source-14) [cite:9](#source-9)

## 9. Agent 调用超时后为什么不能直接重试？如何设计安全的重试与幂等？

- **分类**：生产可靠性
- **难度**：高级
- **考察要点**：未知结果、瞬时错误、指数退避、幂等键、补偿操作
- **参考答案**：
  - 超时表示调用方没有收到结果，不代表服务端一定没有执行。对付款、发消息或创建资源等有副作用的工具直接重试，可能造成重复操作。
  - 只对超时、网络中断、`408`、`429` 和部分 `5xx` 等瞬时错误做有上限的指数退避与随机抖动；参数错误、鉴权失败等永久错误应先修正，不能盲目重试。
  - 写操作应使用稳定的幂等键，例如 `run_id + tool_call_id`，并让下游持久化去重结果；多步骤流程还要保存每步状态，为不可回滚动作设计确认、查询状态或补偿操作。
- **通俗理解**：外卖下单后页面超时，只能说明你没看到结果，不能说明订单没创建；立刻再点一次可能买到两份。正确做法是拿同一个订单号查询或重试，让系统识别这是同一次操作。
- **来源**：[cite:15](#source-15) [cite:8](#source-8)

## 10. 生产 Agent 如何做模型路由，并证明降本没有损害质量？

- **分类**：生产工程
- **难度**：高级
- **考察要点**：任务分层、升级策略、质量门槛、回退与评测
- **参考答案**：
  - 根据任务复杂度、工具需求、风险等级、上下文长度和延迟目标，把分类、抽取、简单问答等任务路由到更快更便宜的模型，把复杂推理和高风险决策升级到能力更强的模型。
  - 路由器可以是显式规则、小模型分类器或专用路由模型，但必须设置低置信度升级、超时回退和预算上限，避免为了省钱把困难任务长期错误分流。
  - 用带任务分层的固定评测集比较路由前后的成功率、严重错误率、P95 延迟和单任务成本，并持续抽样线上流量；只有质量达到预设门槛，成本下降才算有效。
- **通俗理解**：模型路由像医院分诊，普通问题去普通门诊，疑难和高风险病例转专家。不能只看挂号费变便宜，还要确认误诊率没有上升，并为判断不准的病例保留转专家通道。
