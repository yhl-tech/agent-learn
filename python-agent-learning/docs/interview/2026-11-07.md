## 1. RAG 的原文和向量为什么要分开存？向量库能作为唯一数据源吗？

- **分类**：RAG 数据存储
- **难度**：初中级
- **考察要点**：原文存储、向量索引、版本管理、索引重建
- **参考答案**：
  - 向量库主要负责保存 Chunk 的向量、文本片段和检索元数据，适合做语义召回；它不是原始文档、结构化业务事实和版本记录的唯一可信来源。
  - 原始文件及版本可放在对象存储或文档库，结构化事实放关系库或 KV，向量库只保存可由这些源数据重新生成的检索索引。
  - 检索结果通过 `document_id`、`chunk_id` 和版本号回查原文。文档更新或删除时同步更新索引；Embedding 模型更换或索引损坏时，也能从原始数据重新切分和建库。
- **通俗理解**：原文像书的正式存档，向量库像为了快速找书制作的索引卡。索引卡丢了可以重做，但若只剩索引卡，没有完整原文，就很难核对版本和恢复内容。

## 2. Agent Memory 和 RAG 有什么区别？两者可以使用同一个向量库吗？

- **分类**：Memory 与 RAG
- **难度**：初级
- **考察要点**：外部知识、交互记忆、数据来源、存储与检索
- **参考答案**：
  - RAG 主要让模型检索外部知识，例如产品文档、制度和接口说明；Memory 主要保存 Agent 在交互中形成的状态，例如用户偏好、已确认事实、历史任务和可复用经验。
  - 两者都可能使用 Embedding 和向量检索，但“用了同一种存储技术”不代表职责相同。Memory 还要处理作用域、写入、更新、遗忘和跨会话召回，RAG 更关注知识入库、检索和引用。
  - 小型项目可以复用同一个向量数据库服务，但应使用不同集合或命名空间，并分别设置权限、元数据和生命周期，不能把知识库文档与用户记忆混在一起检索。
- **通俗理解**：RAG 像查公司的资料库，Memory 像查看这个用户或项目的个人档案。两者都可以放在同一栋档案馆里，但必须分柜管理，不能把公共手册和个人偏好混成一堆。

## 3. 哪些信息适合写入长期记忆？为什么不能把每轮对话都自动写进去？

- **分类**：长期记忆
- **难度**：初中级
- **考察要点**：写入准则、稳定信息、来源与作用域、更新和删除
- **参考答案**：
  - 适合长期保存的是跨会话仍有价值的信息，例如用户明确确认的稳定偏好、项目固定规则、已验证事实和可复用经验。
  - 一次性请求、临时猜测、未验证结论、敏感信息和外部内容中的指令不应直接写入。全部保存会增加噪声，并让错误或过期信息持续影响后续任务。
  - 写入时应记录用户或项目作用域、来源、更新时间和必要的过期条件；同类信息要去重或更新，且允许用户查看、纠正和删除。
  - 简单项目可优先采用显式触发，例如用户说“请记住”，再逐步增加后台提取；无论哪种方式，都要用样例评估误写和漏写。
- **通俗理解**：长期记忆像联系人备注，适合记“长期使用中文”，不适合记“今天午饭想吃面”。如果每句话都写进去，真正重要的偏好会被临时信息淹没，错误内容也会一直被带到以后。

## 4. Agent 工具应该设计得越细越好吗？怎样判断合适的工具粒度？

- **分类**：工具接口设计
- **难度**：初中级
- **考察要点**：工具粒度、职责边界、调用轮次、真实任务评测
- **参考答案**：
  - 工具不是越细越好。把每个底层 API 都包装成工具，会增加工具数量、选择难度、调用轮次和中间结果 Token；但一个接收自由文本的“万能工具”又会让参数、权限和失败边界不清楚。
  - 每个工具应有清晰且互不重叠的目的，并尽量对应用户能理解的业务动作。经常连续出现、顺序固定且可以统一校验的一组底层调用，可以封装成一个较高层工具。
  - 仍需让关键决策对 Agent 可见，尤其不要把需要用户确认的高风险操作偷偷合并进去。可用真实任务集比较完成率、工具误选率、调用次数、错误率和 Token 消耗，再调整粒度。
- **通俗理解**：工具像办事窗口。每盖一个章都排一次队会很慢，一个窗口包办所有业务又容易说不清；更合适的是按完整业务动作设窗口，同时把付款、删除等关键确认单独保留。
