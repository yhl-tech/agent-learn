## 1. 用户询问实时订单状态、库存或账户余额时，为什么通常不应只用 RAG？

- **分类**：RAG 与 Tool Calling
- **难度**：初中级
- **考察要点**：数据源选型、实时性、精确查询、RAG 与工具协作
- **参考答案**：
  - RAG 更适合从制度、手册、FAQ 等大段非结构化内容中做语义检索；向量库通常保存的是已同步的索引副本，可能存在更新延迟。
  - 订单状态、库存和余额属于实时、结构化且要求精确的数据，应让 Agent 调用受控的业务 API、数据库查询工具或 MCP Tool，并以工具返回结果为准。
  - 两者可以组合：先用 RAG 找业务规则或解释材料，再用工具查询当前数据；路由层应根据问题意图选择数据源，不能把所有信息都塞进向量库。
- **通俗理解**：RAG 像查一本定期更新的业务手册，适合回答“退款规则是什么”；API 像直接询问业务系统，适合回答“我的退款现在到哪一步了”。前者负责解释规则，后者负责给出此刻的准确状态。

## 2. 文档上传接口已经返回成功，为什么还不能立刻让用户检索？应怎样管理状态？

- **分类**：RAG 工程落地
- **难度**：初中级
- **考察要点**：异步索引、文档状态机、可检索条件、失败处理
- **参考答案**：
  - 上传成功通常只表示文件或导入任务已被系统接收，后台仍需完成解析、切块、Embedding 和写入索引；这些步骤未完成时，检索可能返回空结果。
  - 应为文档或导入任务保存稳定 ID，并至少区分 `PENDING`、`PROCESSING`、`READY`、`FAILED` 等状态；只有达到 `READY` 后才标记为可检索。
  - 前端可轮询或接收状态事件展示进度；失败时要保留失败原因并允许重试或重新上传，检索链路则应过滤尚未就绪的文档。
- **通俗理解**：上传成功像快递已经被仓库签收，不代表货物已经完成拆箱、分类和上架。只有系统显示“已上架”，用户搜索时才能真正找到；处理失败也要明确告诉用户卡在哪一步。
