## 1. Agent 需要查询业务数据库时，为什么不能直接给模型一个 `execute_sql` 工具？

- **分类**：Tool Calling 与安全边界
- **难度**：初中级
- **考察要点**：细粒度业务工具、最小权限、租户隔离、SQL 校验、资源限制
- **参考答案**：
  - 模型生成的 SQL 可能漏掉租户条件、访问敏感表、执行写操作或产生超大查询，Prompt 中写“只读、不要越权”不能形成强制安全边界。
  - 对边界明确的场景，应优先封装 `get_order_status`、`query_sales_summary` 等细粒度业务工具，使用审核过的参数化查询；用户身份和 `tenant_id` 必须来自可信登录态，由后端执行权限校验。
  - 确实需要 Text-to-SQL 时，应使用专用只读账号，只开放必要的库、表和列，并在执行前解析 SQL 结构，限制语句类型、表、列和函数，禁止多语句及写操作。
  - 执行层还要设置只读事务、超时、最大返回行数和资源配额，结果进入模型前再做字段裁剪与脱敏。高风险写操作应拆成独立工具并经过权限校验和人工确认。
- **通俗理解**：这像让实习生查报表，不能把数据库管理员钥匙交给他，再只口头叮嘱“别乱改”。更稳妥的做法是只开放几扇需要的门，并由门禁系统限制身份、可看的资料和查询时长。
