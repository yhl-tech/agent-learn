## 1. LLM 推理中的 Prefill 和 Decode 有什么区别？应分别观察哪些延迟指标？

- **分类**：LLM 推理性能
- **难度**：中高级
- **考察要点**：计算瓶颈、TTFT、TPOT、ITL、性能归因
- **参考答案**：
  - Prefill 一次处理全部输入 Token 并建立 KV Cache，矩阵计算并行度较高，通常更偏计算密集；Decode 每一步只生成一个新 Token，却要读取模型权重和历史 KV Cache，通常更受显存带宽限制。
  - TTFT 包含排队、分词和 Prefill，适合观察用户多久看到首个 Token；TPOT 或 ITL 反映 Decode 阶段连续输出是否流畅；端到端延迟还受输出长度影响。
  - 优化前必须先分阶段测量。长 Prompt 导致 TTFT 高时应优先减少输入、缓存前缀或优化 Prefill；TPOT 高时则检查批处理、KV Cache 压力、量化内核和 GPU 利用率。
  - 平均值会掩盖排队和抢占造成的长尾，应按模型、请求类型和输入长度观察 P95/P99。
- **通俗理解**：Prefill 像先把整份材料读完，决定多久能开始回答；Decode 像开始后逐字说出答案，决定说话是否流畅。首字慢和后续卡顿是两类问题，不能只看一个总耗时。

## 2. 静态批处理、动态批处理和 Continuous Batching 有什么区别？

- **分类**：LLM 服务性能
- **难度**：高级
- **考察要点**：请求级批处理、迭代级调度、吞吐与延迟权衡
- **参考答案**：
  - 静态批处理凑齐固定批次后一起运行，必须等最长请求结束才能释放整个批次；动态批处理会在短时间窗口内收集请求，但生成期间批次成员通常仍保持不变。
  - Continuous Batching 在每个 Decode 迭代重新调度，已完成的序列立即退出，等待中的请求可以加入，因此能减少短请求等待长请求造成的空闲，提高 GPU 吞吐。
  - 调度器仍需限制并发序列数和每轮 Token 预算。批次过大可能降低排队吞吐压力，却增加 TTFT、KV Cache 占用和抢占；交互请求与离线任务还应设置优先级或隔离队列。
  - 长 Prefill 会阻塞正在 Decode 的请求时，可通过 Chunked Prefill 将其分段，并在每轮预算中优先保证 Decode，但需要通过负载测试权衡 TTFT 与 ITL。
- **通俗理解**：静态批处理像一车人必须等最慢的人办完事才一起离开，Continuous Batching 则允许办完的人下车、排队的人随时补位。车更少空座，但上车人数和行李量仍要限制，否则所有人都会变慢。

## 3. LLM 的 8-bit 和 4-bit 量化解决什么问题？为什么不能只看显存下降？

- **分类**：LLM 基础与性能
- **难度**：中高级
- **考察要点**：权重压缩、内存带宽、精度损失、硬件与内核支持
- **参考答案**：
  - 量化用更低位宽表示权重或激活，可减少模型显存和内存带宽需求，让更大模型装入有限硬件，并可能提高推理吞吐。8-bit 权重量化通常比 4-bit 更稳健，4-bit 压缩更强但更依赖量化方法和模型特性。
  - 低位权重不代表所有计算都在相同位宽执行，敏感值、LayerNorm 或累加可能保留较高精度；KV Cache 也不会因为权重量化自动缩小，需要单独配置。
  - 实际速度取决于硬件是否支持相应低精度计算、量化内核是否高效，以及反量化开销。模型更小但内核不匹配时，延迟不一定下降。
  - 上线前应在真实任务集比较正确率、工具调用成功率、P95 延迟、吞吐和显存，而不能只比较模型文件大小或通用基准。
- **通俗理解**：量化像把高清图片压缩后存储，文件会更小、传输可能更快，但细节也可能丢失。压缩格式如果没有合适的播放器支持，打开速度甚至未必更快，所以还要用真实任务检查质量和性能。

## 4. 什么是长上下文的 “Lost in the Middle” 问题？如何缓解？

- **分类**：Prompt 与上下文工程
- **难度**：中高级
- **考察要点**：位置偏差、有效上下文、检索与重排、位置鲁棒性评测
- **参考答案**：
  - 模型支持很长的 Context Window，只表示输入能够被接收，不代表所有位置的信息都能被同等可靠地使用。研究发现，关键证据位于长上下文中部时，模型表现可能明显低于证据位于开头或结尾时。
  - 应先通过检索、重排、去重和压缩减少无关内容，只保留当前决策需要的高信号证据；不能把扩大上下文窗口当成替代检索质量的方案。
  - 对必须保留的长材料，可明确标记关键段落、将高优先级证据靠近指令或回答位置，并让模型先提取证据再作答，但这些方法仍需评测验证。
  - 测试集应改变关键证据的位置和上下文长度，检查答案是否稳定，避免只在固定文档顺序下得到虚假的高分。
- **通俗理解**：长上下文像一场很长的会议，模型能听完整场，不代表会同样记住每一分钟。重要信息埋在中间最容易被忽略，所以应先删掉无关内容，并专门测试信息换位置后还能不能答对。

## 5. 向量索引中 HNSW 和 IVF 的原理与选型差异是什么？

- **分类**：RAG 向量检索
- **难度**：高级
- **考察要点**：近似最近邻、图搜索、空间分区、召回与资源权衡
- **参考答案**：
  - HNSW 建立多层邻接图，查询时从稀疏高层逐步走向稠密底层；`M`、`efConstruction` 和 `efSearch` 分别影响图连接、构建成本及查询召回。提高参数通常能提高召回，但会增加内存、建库时间或查询计算。
  - IVF 先用聚类把向量分配到 `nlist` 个倒排桶，查询时只扫描最接近的 `nprobe` 个桶。增大 `nprobe` 通常提高召回并增加延迟，索引还需要先训练聚类中心。
  - HNSW 常适合内存充足、追求低延迟和高召回的场景；IVF 便于结合 PQ 等压缩处理更大规模数据，但对聚类质量和参数更敏感。具体能力还取决于向量数据库实现，例如 Faiss 的 HNSW 索引不支持直接删除。
  - 选型必须在真实数据分布和过滤条件下比较 Recall@K、P95 延迟、内存、构建时间及更新成本，不能只采用默认参数。
- **通俗理解**：HNSW 像沿着熟人关系网逐层找到最接近的人，走得快但要保存很多关系；IVF 像先把人按区域分组，只去几个最可能的区域寻找。多查一些区域或关系通常更准，但也会更慢、更占资源。
- **来源**：[cite:7](#source-7)

## 6. Bi-Encoder、Cross-Encoder 和 ColBERT 的 Late Interaction 有什么区别？

- **分类**：RAG 检索模型
- **难度**：高级
- **考察要点**：单向量检索、联合编码、Token 级交互、精度与成本
- **参考答案**：
  - Bi-Encoder 分别把查询和文档压缩为单个向量，可提前计算文档向量并进行大规模近似检索，速度快，但单次点积表达复杂匹配关系的能力有限。
  - Cross-Encoder 把查询和候选文档一起输入模型，Token 可以充分交互，相关性判断通常更细致，但每个查询都要重新计算每个候选，适合对少量候选精排。
  - ColBERT 为查询和文档保留 Token 级多向量，文档表示仍可离线计算，再通过 MaxSim 做 Late Interaction。它在单向量召回与 Cross-Encoder 精排之间提供了更强的细粒度匹配，但索引体积和查询计算更高。
  - 常见架构是用 BM25、Bi-Encoder 或 Late Interaction 召回，再用 Cross-Encoder 精排；具体层级应由召回率、nDCG、延迟、存储和成本共同决定。
- **通俗理解**：Bi-Encoder 像把每篇文章压成一句摘要再比较，速度快但会丢细节；Cross-Encoder 像把问题和文章逐字对照，最准但很慢。ColBERT 保留多个关键词级线索，试图在速度和细节之间取得平衡。
- **来源**：[cite:8](#source-8)

## 7. Agent 的 Semantic、Episodic 和 Procedural Memory 分别存什么？

- **分类**：Memory
- **难度**：中级
- **考察要点**：事实、经验、规则、存储与召回策略
- **参考答案**：
  - Semantic Memory 保存事实与概念，例如用户偏好、项目约束和实体属性；它不同于“语义检索”，前者描述存什么，后者描述如何查找。
  - Episodic Memory 保存过去发生的任务和行动轨迹，例如某类问题曾采用哪些步骤并得到什么结果，常可转化为 Few-shot 示例供相似任务参考。
  - Procedural Memory 保存完成任务的规则与方法，通常体现在系统 Prompt、工具策略、Agent 代码或模型参数中，而不是普通对话事实。
  - 三类记忆应采用不同 Schema、更新与过期策略。事实要处理冲突和时效，经验要筛选成功且相关的案例，规则变更则要版本化并经过评测，不能把所有历史统一写入向量库。
- **通俗理解**：Semantic Memory 像记住“用户喜欢中文”，Episodic Memory 像记住“上次这样排查成功了”，Procedural Memory 像记住“遇到故障应按哪些步骤处理”。它们用途不同，不能把所有内容都当成聊天记录堆在一起。

## 8. MCP Elicitation 解决什么问题？为什么敏感信息不能用 Form Mode 收集？

- **分类**：MCP
- **难度**：中高级
- **考察要点**：交互式补充信息、Form Mode、URL Mode、用户同意与隐私
- **参考答案**：
  - Elicitation 允许 MCP Server 在处理原始请求期间，通过 Client 向用户补充请求信息；Client 仍控制展示界面、数据发送和用户是否接受、拒绝或取消。
  - Form Mode 用受限 JSON Schema 收集普通结构化数据，Client 可以生成表单并在发送前让用户检查；密码、API Key、Access Token 和支付凭证等敏感信息不得通过该模式传递。
  - 敏感信息应使用 URL Mode，让用户在可信的 HTTPS 页面直接与 Server 或第三方授权服务交互，避免秘密经过 MCP Client、LLM 上下文或客户端日志。
  - Client 必须清楚显示请求来自哪个 Server，URL Mode 还要展示目标域名并取得导航同意；Server 也必须把交互状态与已认证用户安全绑定，并正确处理拒绝和取消。
- **通俗理解**：Elicitation 像办事过程中发现资料不全，由服务窗口请用户补充。普通信息可以在窗口表单填写，但密码和支付信息应跳转到可信机构自己的页面，不能经过中间人转交。

## 9. LangGraph 子图的 Per-invocation、Per-thread 和 Stateless 持久化有什么区别？

- **分类**：LangGraph
- **难度**：中高级
- **考察要点**：子图状态隔离、Checkpointer 继承、多轮记忆、并行调用
- **参考答案**：
  - 子图适合封装可复用流程或子 Agent。父图与子图共享 State Key 时可直接把子图作为节点；Schema 不同时应在包装节点中显式转换输入和输出，避免内部状态泄漏。
  - `checkpointer=None` 是 Per-invocation 默认模式，每次调用从新状态开始，但在本次调用内继承父图的 Checkpointer，因此仍支持 interrupt、恢复和并行隔离。
  - `checkpointer=True` 是 Per-thread 模式，同一 `thread_id` 的多次调用会累积子图状态，只应用于确实需要跨调用记忆的子 Agent；否则容易把独立任务的上下文混在一起。
  - `checkpointer=False` 完全无状态，不支持子图内部的持久化和 interrupt。要使用前两种持久化能力，父图本身也必须配置 Checkpointer。
- **通俗理解**：Per-invocation 像每次请专家都开一张新工单，任务中途可以存档，但下次重新开始；Per-thread 像同一专家持续维护一份客户档案；Stateless 则像一次性问答，结束后不留记录。
- **来源**：[cite:12](#source-12)

## 10. Retry、Circuit Breaker 和 Bulkhead 在 Agent 服务中分别解决什么问题？

- **分类**：生产可靠性
- **难度**：高级
- **考察要点**：瞬时故障、快速失败、资源隔离、级联故障
- **参考答案**：
  - Retry 用于少量瞬时错误，必须有超时、次数上限、退避与随机抖动；它不适合持续故障，也不能替代写操作的幂等保护。
  - Circuit Breaker 在连续失败或超时达到阈值后打开，暂时停止调用故障依赖并立即失败或降级；冷却后以少量探测请求进入 Half-open，成功后再恢复正常流量。
  - Bulkhead 为不同模型、工具、租户或优先级划分独立的并发槽、线程池、连接池或队列，使一个慢工具耗尽资源时，其他能力仍可服务。
  - 三者通常组合使用：先隔离资源，对单次瞬时错误有限重试，持续失败时熔断，并返回缓存、只读结果、部分答案或转异步处理；同时记录熔断状态、拒绝量和降级率。
- **通俗理解**：Retry 是电话占线后隔一会儿再拨，Circuit Breaker 是发现对方长期故障后暂时停止拨号，Bulkhead 则是给不同业务分配独立电话线路。这样一个外部工具坏掉时，不会把整个 Agent 服务的线路都占满。
