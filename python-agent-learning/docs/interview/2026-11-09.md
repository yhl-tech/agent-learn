## 1. Agent 收到用户请求后，怎样判断应该直接回答、追问、调用工具还是拒绝执行？

- **分类**：意图识别与任务路由
- **难度**：初中级
- **考察要点**：请求分类、信息完整性、澄清问题、执行边界
- **参考答案**：
  - 先判断请求属于知识问答、需要外部动作的任务、信息不足的任务，还是超出能力或权限边界的任务，再路由到不同处理分支。
  - 能用现有上下文可靠回答时直接回答；需要实时数据或业务操作时调用对应工具；缺少会改变结果的关键信息时先追问；违法、越权或系统不支持的请求应明确拒绝或转人工。
  - 澄清时只问当前执行必需且影响最大的缺口，并尽量给出候选项，不要让用户把整段需求重新描述一遍。只有业务已经定义明确默认值且风险可控时，程序才能自动补全，并说明所采用的默认值。
  - 路由结果应结构化，例如 `answer`、`clarify`、`tool`、`reject`，再由确定性代码执行对应分支；评测时分别覆盖“可直接处理、需要追问、不应执行”等样例，重点检查误执行。
- **通俗理解**：这像医院分诊，能直接处理的小问题就回答，需要检查的就去对应科室，信息不够先问关键症状，不能处理的则明确说明。关键不是每次都多问，而是别在重要条件不清楚时擅自行动。

## 2. 为什么 Agent API 不应该只返回一段文本？一个基础的请求和响应契约应包含什么？

- **分类**：Agent 工程落地
- **难度**：初中级
- **考察要点**：接口契约、请求与会话标识、结构化状态、错误与扩展字段
- **参考答案**：
  - Agent 的一次调用可能最终回答、要求澄清、等待确认、执行失败或被拒绝。若只返回文本，前端和其他服务只能猜测当前状态，难以可靠地决定展示、重试或继续执行。
  - 基础请求可包含唯一的 `request_id`、用于多轮上下文的 `session_id`、用户输入及经过后端校验的业务上下文；`request_id` 标识本次调用，`session_id` 标识连续会话，不能混用。
  - 基础响应可包含 `request_id`、`session_id`、`status`、`content`、引用、待确认动作以及结构化错误。`status` 至少应区分成功、澄清、等待操作、拒绝和失败，调用方不应从自然语言中解析流程状态。
  - 契约还要约定字段类型、错误码、流式与非流式的结束语义和版本兼容方式。模型输出即使是 JSON，也仍需经过 Schema 和业务校验后才能交给下游使用。
- **通俗理解**：这像快递接口不能只返回一句“正在处理”，还要给出运单号、订单状态和异常原因。文本负责给人看，结构化字段负责让程序知道这是已完成、待补信息还是失败。
