## 1. Agent 的 State 应该保存哪些内容？为什么不能只保存聊天记录？

- **分类**：状态管理
- **难度**：初级
- **考察要点**：任务状态、结构化字段、消息历史、中间结果
- **参考答案**：
  - State 是一次任务执行时共享的工作区，除消息历史外，还可以保存用户目标、当前步骤、已完成步骤、工具结果、错误信息、重试次数和任务状态。
  - 聊天记录适合保留自然语言上下文，但程序若每次都从聊天文本里猜“执行到哪一步”，容易出现遗漏和状态不一致。
  - 应把流程控制需要的关键信息定义成明确字段，例如 `current_step`、`tool_result`、`status`，让节点读取并更新这些字段。
  - State 只保存后续决策需要的信息，大段原始文件或日志可外置存储，在 State 中保留引用。
- **通俗理解**：聊天记录像会议录音，State 像会议任务表。录音能回顾说过什么，但真正推进工作还要看负责人、当前进度和待办事项。

## 2. 工具调用缺少必填参数时，Agent 应该直接猜一个值吗？

- **分类**：Tool Calling
- **难度**：初级
- **考察要点**：必填参数、澄清问题、默认值、参数校验
- **参考答案**：
  - 不能随意猜测会影响结果的必填参数。例如用户只说“查天气”却没有城市，Agent 应向用户追问，而不是默认选择某个城市。
  - 工具 Schema 要明确必填项、类型、枚举和允许范围；只有业务明确规定了默认值时，程序才可以自动补全，并让用户知道使用了什么默认值。
  - 参数生成后仍要由程序侧校验。校验失败时应返回可理解的错误，让 Agent 修正参数或继续询问用户。
  - 涉及金额、收件人、时间和资源 ID 等高影响字段时，执行前还应再次确认。
- **通俗理解**：这像替别人寄快递，缺少地址时不能凭感觉填写。正确做法是先问清楚，再检查地址格式，避免把包裹寄错。
- **来源**：[cite:2](#source-2) [cite:8](#source-8)

## 3. 哪些工具参数不应该让模型生成，而应由后端注入？

- **分类**：工具安全
- **难度**：初中级
- **考察要点**：可信边界、身份与权限、租户隔离、幂等标识
- **参考答案**：
  - 用户身份、`tenant_id`、权限范围、服务端时间、内部密钥和幂等键等可信字段，不应由模型根据对话自行生成。
  - 模型只负责提取业务意图和普通业务参数；后端应从已认证会话、权限系统和运行环境中补充可信字段。
  - 工具执行前还要重新校验用户是否有权访问目标资源，不能因为模型传了某个用户 ID 就直接相信。
  - 这样可以避免模型猜错身份、越权访问，或被用户通过 Prompt 诱导成管理员。
- **通俗理解**：模型可以帮用户填写“想买什么”，但不能自己填写“我是谁、我有什么权限”。身份和门禁信息必须由后台根据真实登录状态提供。
- **来源**：[cite:2](#source-2) [cite:6](#source-6)

## 4. 工具返回内容很长时，为什么不应全部塞回模型上下文？应该怎么处理？

- **分类**：工具设计
- **难度**：初中级
- **考察要点**：上下文预算、结果裁剪、分页、引用
- **参考答案**：
  - 大量无关结果会占用 Token、增加延迟和成本，还会让模型更难找到真正重要的信息。
  - 工具应尽量支持查询条件、字段选择、分页和数量上限，只返回当前任务需要的高信号内容。
  - 对日志、网页和文件可返回摘要、关键片段及来源位置；完整内容放在外部存储，通过文件 ID 或结果 ID 按需继续读取。
  - 裁剪时要保留错误码、关键字段和来源引用，不能为了变短而丢掉后续判断所需的信息。
- **通俗理解**：查一个联系人时，不必把整本通讯录交给 Agent。先返回最相关的几条和页码，需要更多时再继续翻，既省时间也不容易看错。
- **来源**：[cite:5](#source-5) [cite:9](#source-9)

## 5. 一个基础但清晰的 Agent Prompt 通常应包含哪些部分？

- **分类**：Prompt 基础
- **难度**：初级
- **考察要点**：角色、任务、上下文、约束、输出格式
- **参考答案**：
  - 通常要写清角色和目标、当前任务、可用上下文、必须遵守的约束、工具使用边界以及期望的输出格式。
  - 指令应具体、可执行，避免只写“请认真回答”这类无法验证的要求；结构化输出应明确字段、类型和缺失信息的处理方式。
  - 还要说明证据不足、工具失败或用户信息不完整时如何处理，例如拒绝猜测、返回错误或向用户澄清。
  - Prompt 不是一次写完就结束，应先定义成功标准，再用固定测试样本验证和迭代。
- **通俗理解**：Prompt 像给新同事的任务单，要写清他是谁、要做什么、能用哪些资料、哪些事情不能做，以及最后交付什么格式。只说“做好一点”很难得到稳定结果。
- **来源**：[cite:3](#source-3) [cite:10](#source-10)

## 6. RAG 检索不到文档，或检索结果明显不可靠时，系统应该怎么做？

- **分类**：RAG 边界处理
- **难度**：初中级
- **考察要点**：空召回、相关性判断、拒答、查询澄清
- **参考答案**：
  - 不应把空结果交给模型后要求它强行回答，否则模型可能脱离知识库编造内容。
  - 系统应先区分原因：问题含糊、知识库确实没有、过滤条件过严，还是检索链路异常。
  - 对含糊问题可以让用户补充关键词；对可恢复情况可有限地改写查询或放宽合理条件后再检索一次。
  - 仍无可靠证据时，应明确说明知识库中未找到依据，并提供人工咨询、相关主题或补充资料入口。
- **通俗理解**：开卷考试没翻到相关页面时，不能假装书里有答案。可以换一个准确关键词再找一次，仍找不到就直接说明资料不足。
- **来源**：[cite:1](#source-1) [cite:13](#source-13)

## 7. RAG 召回率低时，初中级开发者应按什么顺序排查？

- **分类**：RAG 排障
- **难度**：中级
- **考察要点**：分层定位、文档解析、切分、查询、索引
- **参考答案**：
  - 先准备“问题到正确文档”的小型测试集，确认是没召回正确内容，而不是召回正确但生成阶段答错。
  - 再按链路排查：原文是否入库、解析是否丢字或顺序错、Chunk 是否切断关键信息、元数据过滤是否误删、文档和查询是否使用同一 Embedding 配置。
  - 随后检查用户问题是否含糊，必要时做简单查询改写，并比较关键词检索、向量检索或混合检索的结果。
  - 每次只改变一个因素，用 Recall@K 或命中率比较前后效果，避免同时改很多参数后无法判断原因。
- **通俗理解**：找不到书时，先确认书是否真的进了图书馆，再看目录是否写错、分类是否放错，最后才调整搜索方法。一步一步排查，才能知道问题出在哪一层。
- **来源**：[cite:4](#source-4) [cite:11](#source-11) [cite:14](#source-14)

## 8. RAG 中的 Top-K 和相似度阈值分别有什么作用？

- **分类**：RAG 检索
- **难度**：初中级
- **考察要点**：候选数量、最低相关性、召回与噪声
- **参考答案**：
  - Top-K 控制最多返回多少个候选 Chunk；相似度阈值控制候选至少要达到多相关才允许返回。
  - K 太小可能漏掉正确资料，太大会引入噪声并增加上下文成本；阈值太高可能空召回，太低则容易把无关内容交给模型。
  - 相似度分数不是通用概率，不同 Embedding 模型和向量库的分数范围可能不同，不能照搬固定阈值。
  - 应使用真实问题集比较命中率、答案质量和 Token 成本，再确定 K 和阈值，并为无结果情况设计明确兜底。
- **通俗理解**：Top-K 像规定最多拿几本候选书，阈值像规定相关程度低于多少就不拿。拿得太少可能漏书，拿得太多又会让无关内容干扰阅读。
- **来源**：[cite:1](#source-1) [cite:12](#source-12)

## 9. RAG 入库时，为什么要给每个 Chunk 保存元数据？常见字段有哪些？

- **分类**：RAG 数据处理
- **难度**：初级
- **考察要点**：来源定位、过滤、版本、可追溯性
- **参考答案**：
  - Chunk 只有正文而没有元数据时，系统很难知道它来自哪个文件、哪一页，也难以按权限、版本或业务分类过滤。
  - 常见字段包括 `document_id`、`chunk_id`、文件名或 URL、页码或段落位置、标题层级、更新时间、版本和权限范围。
  - 检索时可先用元数据限定知识库、文档类型、时间或权限，再做相似度搜索；生成答案时还能用来源字段展示引用。
  - 元数据应来自可信的入库流程，字段命名和类型要稳定，避免同一含义在不同文档中使用不同格式。
- **通俗理解**：Chunk 像从书里剪下的一段文字，元数据就是书名、页码和版本标签。没有标签，即使内容找对了，也不知道出处，更无法判断用户能不能看。
- **来源**：[cite:2](#source-2) [cite:12](#source-12)

## 10. 线上发现一个 Agent Badcase 后，怎样把它变成可持续改进的闭环？

- **分类**：Agent 评估
- **难度**：中级
- **考察要点**：Trace 定位、问题分类、回归样本、修复验证
- **参考答案**：
  - 先保存脱敏后的输入、输出和 Trace，定位首次出错的环节，例如检索错误、工具选择错误、参数错误、状态推进错误或最终生成错误。
  - 将问题按根因分类，只修对应层，不要遇到所有问题都修改 Prompt。
  - 把 Badcase 整理成包含输入、期望结果和检查规则的离线评测样本；修复后同时运行原有回归集，避免新方案解决一个问题却破坏其他场景。
  - 上线后继续观察同类错误率、任务成功率和用户反馈，确认修复在真实流量中有效。
- **通俗理解**：Badcase 像一次错题，不能只改当次答案。要找到错在哪一步，把它加入错题本，之后每次改方案都重新测试，确保同类问题不会再犯。
