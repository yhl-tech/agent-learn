## 1. Agent 与固定工作流的核心区别是什么？什么时候不应该使用 Agent？

- **分类**：Agent 基础
- **难度**：初级
- **考察要点**：控制流归属、确定性、成本与可靠性权衡
- **参考答案**：
  - 固定工作流由代码预先决定执行路径；Agent 由模型根据当前状态、工具结果和环境反馈动态决定下一步。
  - 当步骤稳定、规则明确、输出可通过普通代码或单次模型调用完成时，应优先使用确定性工作流。
  - Agent 适合路径无法预先穷举、需要根据运行时信息持续决策的开放任务，但会增加延迟、成本、调试难度和错误累积风险。
- **通俗理解**：固定工作流像按固定站点行驶的地铁，路线早已确定；Agent 更像司机，会根据堵车、天气等实时情况改路线。如果事情每次都按相同步骤完成，就没必要请 Agent 自己判断，普通程序会更快、更稳、更省钱。

## 2. 请解释 ReAct 循环，并说明如何避免 Agent 无限循环

- **分类**：Agent 运行机制
- **难度**：中级
- **考察要点**：Reason-Act-Observe、环境反馈、终止条件
- **参考答案**：
  - ReAct 的基本循环是：根据当前状态推理，选择并调用工具，读取真实观察结果，再决定继续调用工具还是输出最终答案。
  - 工具结果必须回写上下文，后续决策应以真实结果为依据，不能把模型猜测当成环境事实。
  - 生产环境需要设置最大步数、总耗时和成本预算，并检测重复工具调用、状态无进展和连续失败；达到阈值后应安全终止、降级或转人工。
- **通俗理解**：ReAct 就是“想一下、做一步、看结果”，然后再决定下一步。例如查天气时，Agent 先调用天气工具，看到结果后再回答，而不是自己猜；同时要限制最多尝试几次，避免它一直重复查询。

## 3. Function Calling 与完整的工具调用 Agent 有什么区别？工具接口应如何设计？

- **分类**：Tool Calling
- **难度**：中级
- **考察要点**：模型与运行时边界、Schema、错误处理、工具粒度
- **参考答案**：
  - Function Calling 是模型生成结构化调用请求的能力；真正执行代码、校验参数、控制权限和处理副作用的是应用运行时。
  - 完整 Agent 还需要控制循环、状态管理、工具执行、错误恢复、终止条件和可观测性。
  - 工具应有单一且清晰的职责、明确的名称和参数 Schema，并返回对模型有用的结构化结果或可恢复错误。
  - 工具并非越多越好。功能重叠或粒度过细会增加选错工具、参数错误和上下文消耗，应通过真实任务评测逐步调整。
- **通俗理解**：Function Calling 只是模型填写了一张“调用哪个工具、传什么参数”的工单，真正干活的是程序。Agent 则像工单调度员，不仅会填单，还会执行、查看结果、处理失败并决定是否继续；工具名称和用途越清楚，它越不容易选错。

## 4. 普通 RAG 与 Agentic RAG 有什么区别？什么时候值得引入 Agentic RAG？

- **分类**：RAG
- **难度**：中级
- **考察要点**：固定检索链路、动态规划、多跳检索、复杂度边界
- **参考答案**：
  - 普通 RAG 通常执行固定的“查询、检索、生成”流程，适合 FAQ、知识库问答等单跳任务。
  - Agentic RAG 让模型决定是否改写查询、拆解问题、选择数据源、重复检索和检查证据，因此更适合多跳问题或首次检索不足的场景。
  - 引入前应先优化文档解析、切分、混合检索、重排和评测集。若固定 RAG 已能稳定满足目标，Agentic RAG 只会增加成本、延迟和不可预测性。
- **通俗理解**：普通 RAG 像去资料库查一次关键词，然后根据查到的内容回答；Agentic RAG 像研究员，发现资料不够时会换关键词、拆问题并继续查。简单问答查一次就够，只有复杂问题需要多轮找证据时，才值得使用 Agentic RAG。

## 5. LangGraph 的 State、Checkpointer 和 Store 分别解决什么问题？

- **分类**：LangGraph
- **难度**：中高级
- **考察要点**：显式状态、线程级持久化、跨线程长期记忆
- **参考答案**：
  - `State` 保存图中节点需要共享和更新的业务状态，应保持结构明确并可序列化。
  - `Checkpointer` 按线程保存图状态快照，用于会话连续性、故障恢复、时间旅行和 Human-in-the-loop。
  - `Store` 保存图状态之外的长期数据，例如跨会话的用户偏好、事实和共享知识。
  - 生产环境不能依赖纯内存 Checkpointer；长任务还需要检查点保留和清理策略，避免状态无限增长。
- **通俗理解**：`State` 像正在填写的工作表，记录任务当前做到哪一步；`Checkpointer` 像游戏存档，程序中断后可以从存档继续；`Store` 像长期档案柜，保存用户偏好等跨任务仍要使用的信息。三者分别解决“当前有什么”“如何接着做”和“以后还要记住什么”。

## 6. Agent 的短期记忆和长期记忆有什么区别？如何避免上下文持续膨胀？

- **分类**：Memory
- **难度**：中高级
- **考察要点**：记忆作用域、写入策略、检索策略、上下文预算
- **参考答案**：
  - 短期记忆服务于当前线程或任务，通常包含对话、步骤状态和近期工具结果；长期记忆跨线程保存稳定偏好、事实或历史经验。
  - 长期记忆不应简单等同于“把所有历史塞进 Prompt”，而应通过结构化存储、检索、元数据过滤和按需召回使用。
  - 控制上下文可组合使用：压缩旧对话、仅检索相关记忆、把大体积工具结果外置并保留引用、删除已无决策价值的中间步骤。
  - 写入长期记忆前要判断内容是否稳定、是否需要过期或覆盖，并处理冲突、隐私和用户删除请求。
- **通俗理解**：短期记忆像桌面上正在使用的便签，任务结束后可能就不需要了；长期记忆像档案柜，保存以后还会用到的信息。不能每次都把整个档案柜搬到桌上，而应只取出当前问题相关的几份资料，否则上下文会越来越长、越来越贵。
- **来源**：[cite:2](#source-2) [cite:3](#source-3) [cite:5](#source-5)

## 7. MCP 与普通 Function Calling 有什么区别？MCP 的 Host、Client、Server 各自负责什么？

- **分类**：MCP
- **难度**：中级
- **考察要点**：协议标准化、组件职责、安全边界、能力发现
- **参考答案**：
  - Function Calling 描述模型如何请求调用某个函数；MCP 进一步标准化应用与外部工具、资源和 Prompt 服务之间的连接方式。
  - Host 是承载模型的应用，负责权限、授权、安全策略和上下文聚合；Client 由 Host 创建，并与一个 Server 通信；Server 暴露聚焦的工具、资源和 Prompt 能力。
  - MCP 的价值在于减少每个 Agent 与每个外部系统之间的定制集成，但它不会自动解决授权、最小权限、数据隔离和工具安全问题。
  - 能力必须由双方显式声明，Host 仍应决定向 Server 暴露哪些上下文以及是否允许执行高风险操作。
- **通俗理解**：Function Calling 像某个应用自己约定的工具调用格式，MCP 更像统一的 USB 标准，让不同应用都能接入符合标准的工具服务。Host 是总管，Client 是连接线，Server 是提供能力的设备；能连上不代表什么都能做，权限仍要由 Host 严格控制。

## 8. 什么时候应该从单 Agent 升级为多 Agent？常见代价是什么？

- **分类**：多 Agent 架构
- **难度**：高级
- **考察要点**：职责拆分、并行性、上下文冲突、协调成本
- **参考答案**：
  - 默认应从单 Agent 开始。只有在工具和指令过多导致选择质量下降、存在明确的专业边界，或独立子任务能够并行并显著降低总耗时时，才考虑多 Agent。
  - 常见模式包括 Supervisor-Worker、Router-Specialists 和 Orchestrator-Workers。需要显式定义共享状态、消息边界、最大交接次数和最终汇总责任。
  - 代价包括更多模型调用、更高延迟与成本、错误跨 Agent 传播、无限交接、上下文不一致，以及更复杂的追踪和评测。
- **通俗理解**：单 Agent 像一个人独立完成任务，多 Agent 像组建团队并让不同专家分工。只有一个人已经忙不过来、专业职责明显不同或任务能并行时，团队才可能更高效；否则沟通、交接和管理成本反而会让事情更复杂。

## 9. 如何系统评估一个非确定性的 Agent？

- **分类**：评估与可观测性
- **难度**：高级
- **考察要点**：结果评估、轨迹评估、回归集、线上指标
- **参考答案**：
  - 评估不能只看最终文案。至少应覆盖任务是否完成、工具选择和参数是否正确、执行轨迹是否合理、是否违反安全规则，以及成本和延迟是否可接受。
  - 建立包含正常、边界、失败和攻击场景的固定数据集，并在 Prompt、模型、工具或路由变更后执行回归评测。
  - 对 Agent 运行记录端到端 Trace，包含模型调用、工具调用、Guardrail、Handoff 和状态变化，以定位首次偏离正确路径的步骤。
  - LLM-as-Judge 应使用明确评分规则，并用人工样本校准；关键结果尽量使用确定性检查或真实系统最终状态验证。
- **通俗理解**：评估 Agent 不能只看“最后答得像不像”，还要看它是否选对工具、走对步骤、花费是否合理。就像批改数学题既看答案也看过程，还要保留完整草稿，出错时才能找到是从哪一步开始错的。

## 10. 如何防御 Prompt Injection 和 Agent 的 Excessive Agency？

- **分类**：安全与 Guardrail
- **难度**：高级
- **考察要点**：不可信输入、最小权限、完整鉴权、人工审批、纵深防御
- **参考答案**：
  - 用户输入、检索文档、网页内容、工具输出和其他 Agent 消息都应视为不可信数据，不能仅依赖系统 Prompt 声明“忽略恶意指令”。
  - 工具应遵循最小功能和最小权限原则，避免向模型暴露开放式高权限能力；下游系统必须独立执行身份认证和授权，不能让模型决定权限。
  - 对删除、付款、外发消息、生产写入等高影响操作，在执行前设置阻塞式校验和人工审批；审批前后的副作用要保证幂等。
  - 输入、输出和每次工具调用都可以设置 Guardrail，同时配合沙箱、速率限制、审计日志、异常检测和安全回归测试。
- **通俗理解**：可以把 Agent 看成会读很多外部资料的实习生，其中某份资料可能故意骗它做危险操作。安全不能只靠叮嘱它“别上当”，还要限制它能用的权限，并让付款、删除数据等高风险动作必须经过人工确认。
