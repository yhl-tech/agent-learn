## 1. Context Engineering 与 Prompt Engineering 有什么区别？如何控制 Agent 的上下文质量？

- **分类**：Prompt 与上下文工程
- **难度**：中级
- **考察要点**：上下文组成、注意力预算、动态裁剪、信息优先级
- **参考答案**：
  - Prompt Engineering 主要优化指令和示例的写法；Context Engineering 管理一次推理时模型能看到的全部信息，包括系统指令、工具定义、检索证据、消息历史、记忆和剩余 Token 预算。
  - 上下文不是越长越好。无关、陈旧或互相冲突的信息会挤占注意力，应保留完成当前决策所需的最小高信号集合。
  - 长任务可结合按需检索、工具结果外置、旧历史压缩和结构化笔记；同时记录最终组装后的上下文和截断情况，便于定位指令丢失或证据被挤出的问题。
- **通俗理解**：Prompt Engineering 像把任务说明写清楚，Context Engineering 则像整理整个工作台，决定说明书、资料、工具和历史记录中哪些要摆在眼前。桌上堆满资料不一定更好，关键是让当前最有用的信息容易被看到。

## 2. 如何减少并检测 LLM 的无依据陈述？为什么“要求附引用”仍不够？

- **分类**：可靠性与 Grounding
- **难度**：中高级
- **考察要点**：可回答性、证据约束、引用校验、拒答策略
- **参考答案**：
  - 先定义可回答边界：要求模型只依据给定证据回答，证据不足时明确拒答或请求补充信息，而不是强行生成完整答案。
  - 可先提取支持性原文，再生成结论；生成后把答案拆成事实声明，逐条检查是否存在支持片段，并删除或标记无法验证的声明。
  - “带引用”只约束了输出形式，模型仍可能引用错误来源或让引用与结论不匹配。应用侧还要验证来源是否真实、引用片段是否存在，以及片段是否真正支持对应结论。
  - 高风险结果应使用确定性规则、权威数据源或人工复核，不能把模型自检当作最终事实保证。
- **通俗理解**：让模型写脚注，就像要求学生在答案后列参考书，并不能证明他真的从那一页得出了结论。还要逐条核对“书里有没有这句话”和“这句话能不能支持答案”，没有证据时宁可回答不知道。

## 3. Agent 何时可以并行调用工具，何时必须串行执行？

- **分类**：Tool Calling
- **难度**：中级
- **考察要点**：数据依赖、副作用、延迟优化、结果关联
- **参考答案**：
  - 互不依赖、只读且结果可独立解释的调用适合并行，例如同时查询天气和汇率；后一步参数依赖前一步结果时必须串行。
  - 有共享资源或副作用的操作不能仅因“技术上可并发”就并行，例如先创建订单再付款、同时修改同一记录。应显式描述依赖关系，并用锁、版本校验或事务保护共享状态。
  - 运行时必须用唯一 `tool_call_id` 关联每个请求和结果，分别处理超时与失败；部分成功时要根据业务语义决定继续、补偿还是整体终止。
  - 并行化应以端到端延迟和正确率评测为依据，不能让模型自行猜测隐含依赖。
- **通俗理解**：并行调用像同时让两个人查天气和汇率，彼此不依赖就能更快完成。若第二件事必须拿到第一件事的结果，或两个人会同时修改同一份账本，就必须排好顺序并保护共享数据。

## 4. 当 Agent 有几百个工具时，为什么不应把所有工具定义都放进 Prompt？应如何做 Tool Retrieval？

- **分类**：Tool Calling
- **难度**：中高级
- **考察要点**：工具选择准确率、上下文占用、动态发现、召回评估
- **参考答案**：
  - 大量工具定义会消耗上下文，并增加名称相近、职责重叠时的误选概率。应让少量高频基础工具常驻，其余工具按当前任务动态检索。
  - 可用关键词、BM25 或向量检索搜索工具名称、描述和参数说明，召回少量候选后，再由模型完成最终选择和参数生成。
  - 工具描述必须清楚说明用途、禁用场景、参数语义和限制；检索层还要做命名空间、权限和租户过滤，不能把用户无权使用的工具暴露给模型。
  - 评估应拆分为工具召回率、最终选择准确率、参数正确率和端到端任务成功率，避免只优化检索相似度。
- **通俗理解**：这像大型仓库不会把所有工具都堆到工人桌上，而是先根据任务从目录中找出几件可能有用的工具。目录既要找得准，也不能把没有权限使用的设备交出来。
- **来源**：[cite:2](#source-2) [cite:6](#source-6)

## 5. 生产 RAG 为什么常用 Hybrid Search？BM25、向量检索、RRF 和 Reranker 分别做什么？

- **分类**：RAG
- **难度**：中高级
- **考察要点**：稀疏与稠密检索、结果融合、精排、召回与延迟权衡
- **参考答案**：
  - BM25 等关键词检索擅长产品编号、专有名词和精确词匹配；向量检索擅长语义相近但措辞不同的内容，两者覆盖的失败模式不同。
  - Hybrid Search 通常并行执行稀疏和稠密检索，再用 RRF 按各结果在列表中的名次融合，避免直接比较不可比的原始分数。
  - Reranker 对合并后的较小候选集做更精细的查询与文档相关性判断，再选出最终上下文；它通常提高排序质量，但会增加延迟和成本。
  - `top_k`、融合权重和重排候选数必须在真实查询集上按 Recall、nDCG、答案正确率、延迟与成本共同调优。
- **通俗理解**：关键词检索像按书名和编号找书，向量检索像按内容意思找书；两种方法先各自找一批，再合并名单。Reranker 像图书管理员对候选书逐本复核，把真正最相关的放到前面。

## 6. 多租户 RAG 如何防止检索到其他用户无权查看的文档？

- **分类**：RAG 安全
- **难度**：高级
- **考察要点**：文档级权限、检索前过滤、身份可信边界、缓存隔离
- **参考答案**：
  - 索引时要给每个文档或 Chunk 写入租户、用户组、资源 ACL 等可过滤元数据；查询时由可信后端根据已认证身份生成过滤条件，并在向量或关键词检索阶段强制执行。
  - 不能先检索全库再让 LLM 删除无权内容，因为未授权文本此时已经进入应用或模型上下文；也不能信任用户输入或模型生成的 `tenant_id`。
  - 权限变更要同步更新索引元数据，并确保检索缓存、Embedding 缓存和答案缓存的键包含租户与权限作用域，避免跨租户复用。
  - 还应测试空权限、权限撤销、共享文档、混合检索和缓存命中等场景，并记录最终返回的文档 ID 供审计。
- **通俗理解**：这像公司档案室必须在取文件时就查门禁，不能先把所有文件交给员工，再要求他自己丢掉无权查看的部分。缓存也要分柜保存，否则上一位用户查过的机密内容可能被下一位直接拿到。

## 7. LangGraph 的 Reducer 解决什么问题？并行节点写同一个 State Key 时会发生什么？

- **分类**：LangGraph
- **难度**：中高级
- **考察要点**：部分状态更新、归并语义、并行冲突、幂等 Reducer
- **参考答案**：
  - LangGraph 节点应返回部分状态更新；每个 State Key 的 Reducer 决定新值如何与旧值合并。没有显式 Reducer 时，更新通常覆盖旧值。
  - 多个并行节点在同一个 Super-step 写同一 Key 时，如果系统不知道如何合并，就会产生并发更新错误；列表累积、计数求和或按 ID 更新消息应配置对应 Reducer。
  - Reducer 应满足确定、可结合等要求，最好对重放保持幂等；否则并行执行顺序或失败恢复可能导致不同结果或重复数据。
  - 不应给所有字段统一使用追加逻辑。状态、集合、计数和最后写入值具有不同语义，应逐字段定义归并规则。
- **通俗理解**：Reducer 像多人同时填写汇总表时的合并规则：有的列要相加，有的要追加，有的只能保留一个最终值。没有规则时，系统无法判断两个并行结果应该覆盖还是合并。

## 8. MCP 的 stdio 与 Streamable HTTP 适用于什么场景？远程 MCP Server 要注意哪些安全边界？

- **分类**：MCP
- **难度**：高级
- **考察要点**：传输选择、Origin 校验、OAuth、Token Audience、最小权限
- **参考答案**：
  - `stdio` 适合 Host 启动并管理的本地子进程，消息走标准输入输出，凭证通常来自受控环境；Streamable HTTP 适合独立部署、支持多个远程客户端的服务。
  - HTTP Server 应校验 `Origin` 防止 DNS Rebinding，本地服务只绑定回环地址，生产环境使用 HTTPS、认证和最小 Scope。
  - MCP Server 必须验证 Access Token 的签发方、有效期、Audience 和 Scope，只接受明确签发给自己的 Token，不能把客户端 Token 不经验证地透传到下游系统。
  - 远程发现和 OAuth 元数据请求还要防 SSRF，并对重定向、私网地址和云元数据地址进行限制。
- **通俗理解**：`stdio` 像应用内部拉的一根专用线，Streamable HTTP 像对外开放的服务窗口。窗口一旦能被远程访问，就必须验明来客、检查通行证只对当前服务有效，并防止对方诱导服务去访问内网地址。

## 9. 生产 Agent 的 Trace 应记录哪些信息？为什么不能默认记录完整 Prompt 和工具结果？

- **分类**：可观测性
- **难度**：高级
- **考察要点**：Span 层级、关联 ID、Token 与延迟、隐私与成本
- **参考答案**：
  - 一个 Agent Run 应作为根 Span，下面关联每次模型调用、工具调用、检索、Guardrail 和子 Agent Span，并保留 `run_id`、`thread_id`、模型与 Prompt 版本。
  - 每个 Span 至少记录开始与结束时间、状态、错误类型、输入输出 Token、成本、重试次数和工具名称；这样才能定位延迟、费用或错误首次出现在哪一步。
  - 完整 Prompt、工具参数和结果可能包含个人信息、密钥与业务数据，也会显著增加日志体积，因此应默认只记录元数据，对内容采集实行显式开关、脱敏、访问控制和保留期限。
  - Trace 用于单次故障诊断，Metrics 用于观察成功率、P95 延迟、Token 和成本趋势，二者应通过稳定标签关联，但避免把用户 ID 等高基数字段直接作为指标标签。
- **通俗理解**：Trace 像快递包裹经过每个中转站的明细，能看出到底在哪一站延误或丢失；Metrics 像整个物流网络的日报。包裹内容可能很敏感，所以默认记录路线和耗时即可，需要查看内容时还要经过脱敏和授权。

## 10. 高并发 Agent 服务如何处理模型 API 的 RPM、TPM 和突发流量限制？

- **分类**：性能与生产工程
- **难度**：高级
- **考察要点**：双维度限流、背压、平滑流量、降级与容量规划
- **参考答案**：
  - RPM 限制请求数量，TPM 限制 Token 消耗；只按并发数或请求数限流仍可能被少量长 Prompt 耗尽 Token 配额。
  - 客户端应在发送前进行准入控制：用 Token Bucket 平滑 RPM/TPM，用 Semaphore 限制在途请求，并设置有界队列、排队超时和取消传播，形成背压。
  - `429` 或瞬时 `5xx` 可按 `Retry-After` 做有上限的指数退避和随机抖动，但重试不能替代主动限流，否则高峰期会形成请求堆积和重试风暴。
  - 队列接近上限时应拒绝低优先级任务、降级到更小模型、转异步批处理或快速失败；容量规划要同时观察排队时间、RPM、TPM、并发数和 P95/P99 延迟。
- **通俗理解**：模型服务像一条既限制车辆数量、又限制总载重量的道路，十辆空车和十辆重卡造成的压力不同。入口要提前放行和排队，路堵时还要限流或改道，不能让所有车辆不断掉头重试。
