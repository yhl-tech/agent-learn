## 1. ReAct 与 Plan-and-Execute 有什么区别？应该如何选型？

- **分类**：Agent 规划
- **难度**：中高级
- **考察要点**：逐步决策、显式规划、动态重规划、成本与鲁棒性
- **参考答案**：
  - ReAct 每轮根据最新观察选择一个动作，适合路径难以提前确定、环境反馈可能随时改变的任务，但通常每次工具调用前都需要模型重新决策。
  - Plan-and-Execute 先由 Planner 生成多步计划，再由 Executor 逐项执行，并在结果偏离预期时重规划。它能让子任务使用更小模型或确定性代码，也便于发现可并行的无依赖步骤。
  - 计划并不保证正确，过早生成的长计划可能建立在错误假设上。稳定且可拆解的长任务适合 Plan-and-Execute，探索性强或反馈变化快的任务更适合 ReAct，也可以采用“短计划、执行、再规划”的混合方式。
- **通俗理解**：ReAct 像边走边看路口决定下一步，Plan-and-Execute 像先列好行程再逐站完成。路况变化大时要频繁看现场，路线稳定且步骤多时先规划通常更省时间。

## 2. Zero-shot、One-shot 和 Few-shot Prompt 应如何选择？示例越多越好吗？

- **分类**：Prompt
- **难度**：初级
- **考察要点**：示例数量、任务歧义、边界覆盖、上下文成本
- **参考答案**：
  - Zero-shot 只给指令，不提供示例；One-shot 给一个示例；Few-shot 给少量输入输出示例，让模型从上下文中学习期望的格式、语气、范围或分类边界。
  - 应先用清晰指令测试 Zero-shot；当任务边界难以文字描述、输出不稳定或需要展示特殊格式时，再加入具有代表性且格式一致的示例，并覆盖容易混淆的正反边界。
  - 示例不是越多越好。过多或偏置的示例会占用上下文、放大偶然模式，甚至让模型机械模仿；最终数量应通过固定评测集比较准确率、稳定性、延迟和 Token 成本确定。
- **通俗理解**：Zero-shot 像只告诉新人规则，Few-shot 则再给他看几份合格样品。样品要典型而且一致，堆很多相似或错误样品反而会把人带偏。

## 3. Python 的 GIL 会怎样影响 Agent 服务？线程、asyncio 和多进程应如何选择？

- **分类**：Python Agent
- **难度**：中级
- **考察要点**：GIL、I/O 并发、CPU 并行、共享内存与隔离
- **参考答案**：
  - 默认 CPython 中，GIL 使同一进程通常只有一个线程执行 Python 字节码，因此增加线程不能让纯 Python CPU 密集任务获得真正的多核并行；Python 3.13 起虽有可关闭 GIL 的 free-threaded 构建，但并非默认。
  - LLM API、数据库和网络工具主要在等待 I/O，可使用 `asyncio` 承载大量协程；已有的同步阻塞 SDK 可放入受控线程池，因为阻塞等待期间线程仍能提高并发。
  - PDF 解析、重排模型推理或大规模文本计算等 CPU 密集工作应使用多进程、原生库或独立任务服务。选型还要考虑取消、超时、共享状态、序列化成本和进程故障隔离，而不能只看并发数量。
- **通俗理解**：GIL 像一个只允许一人使用的 Python 计算台，多开线程也不能让几个人同时做纯计算。等待网络时大家可以轮流使用它，但重计算最好分到多个独立工作间。

## 4. RAG 预处理复杂 PDF、扫描件和表格时，为什么不能只做纯文本提取？

- **分类**：RAG 数据处理
- **难度**：中高级
- **考察要点**：OCR、版面结构、阅读顺序、表格语义、质量检测
- **参考答案**：
  - PDF 保存的是页面绘制结果，不一定包含可靠的段落和阅读顺序；扫描件还需要 OCR。直接拼接文本容易打乱双栏内容、页眉页脚、标题层级和表格行列关系。
  - 应先识别文档类型，再用 Layout/OCR 模型提取文本、标题、段落、页码、表格和坐标等结构；切分时沿章节和语义边界处理，表格应整体保留或转为带表头的结构化表示，并保存来源定位元数据。
  - 入库前要抽样检查 OCR 字错率、阅读顺序、表格完整性和空页，并对低置信度页面降级或人工复核。检索评测还应单独包含跨页表格、图片文字和多栏文档等失败场景。
- **通俗理解**：复杂 PDF 像把报纸拍成照片，只把识别出的字连起来，会把左右两栏和表格内容混在一起。先恢复版面和行列关系，再切成检索片段，才能让模型读懂原来的意思。

## 5. RAG 中的 Query Rewriting、Multi-Query 和 HyDE 分别解决什么问题？有什么风险？

- **分类**：RAG 检索增强
- **难度**：中高级
- **考察要点**：查询纠错与扩展、多路召回、假设文档、意图漂移
- **参考答案**：
  - Query Rewriting 对原问题做纠错、消歧、补全同义词或改写为更适合检索的表达；Multi-Query 生成多个不同角度的查询并合并结果，用更高成本换取召回覆盖。
  - HyDE 先让模型生成一段“假设答案文档”，再对该文档做 Embedding，以其语义邻域寻找真实文档；假设文档只用于检索，不能作为回答证据。
  - 改写可能丢失产品编号、否定词、时间范围等关键约束，HyDE 也可能把错误假设带入检索方向。因此应保留原查询共同检索、限制改写数量，记录各路来源，并在真实查询集上评估 Recall、精度、延迟和意图漂移。
- **通俗理解**：查询改写像把含糊的问法换成资料库更容易听懂的说法，Multi-Query 像同时用几组关键词寻找。HyDE 则先写一段“可能长这样”的答案去找相似真资料，但这张草稿本身不能当证据。

## 6. Parent-Document Retrieval 为什么能兼顾检索精度和上下文完整性？

- **分类**：RAG 检索
- **难度**：中级
- **考察要点**：子块索引、父块回溯、上下文扩展、去重与预算
- **参考答案**：
  - 小 Chunk 主题更集中，Embedding 更容易准确匹配查询，但返回后可能缺少前因后果；大 Chunk 上下文完整，却可能混入多个主题而降低向量匹配精度。
  - Parent-Document Retrieval 将小的 Child Chunk 建入向量索引，并保存它到较大 Parent Chunk 或原文的映射。检索先命中 Child，再通过 `parent_id` 回溯并返回 Parent，从而实现“小块找得准，大块读得懂”。
  - 多个 Child 可能指向同一 Parent，因此要按父 ID 去重并控制总 Token；父块也不能无限大，否则会重新引入无关上下文和成本问题。
- **通俗理解**：这像先用书中的一句话精确定位，再把它所在的完整段落交给读者。定位用小纸条更准，理解时则需要把周围内容一起拿回来。

## 7. 知识库频繁更新时，如何设计增量索引并避免向量数据过期？

- **分类**：RAG 生产工程
- **难度**：高级
- **考察要点**：变更捕获、选择性重算、删除同步、幂等与一致性
- **参考答案**：
  - 使用 Change Feed、CDC、消息事件或高水位时间戳捕获新增、更新和删除，不应每次全量重建。为文档保存源版本、内容哈希、Embedding 模型版本和索引状态，只有参与向量化的内容变化时才重新切分和生成 Embedding。
  - 消费者要持久化处理游标并按文档 ID 与版本幂等 Upsert；删除应传播 Tombstone，避免源文档已删但旧 Chunk 仍可召回。高流量更新可通过队列削峰、批量 Embedding、限速和死信队列处理。
  - 查询侧应只读取完整发布的版本。更换切分规则或 Embedding 模型时，通常建立新索引并回填、验证后切换别名，避免新旧维度和表示空间混用。
- **通俗理解**：增量索引像通讯录同步，只更新真正改过的联系人，而不是每天重抄整本。每条记录还要带版本号，删除和失败也要被记住，否则搜索会继续找到过期内容。

## 8. LangGraph 的 interrupt 如何实现 Human-in-the-loop？恢复执行时最容易踩什么坑？

- **分类**：LangGraph
- **难度**：高级
- **考察要点**：动态暂停、Checkpoint、thread_id、恢复重放、副作用幂等
- **参考答案**：
  - 节点调用 `interrupt()` 后，LangGraph 通过 Checkpointer 保存状态并把可序列化的审批信息返回调用方；外部人员完成审核后，用相同 `thread_id` 和 `Command(resume=...)` 恢复，恢复值会成为 `interrupt()` 的返回值。
  - `interrupt` 适合付款、删除、生产写入等执行前审批，也可让人工修改模型输出或补充缺失信息。生产环境需要持久化 Checkpointer，并校验恢复人的身份、权限和输入 Schema。
  - 恢复时包含 `interrupt()` 的节点会从头重新执行，因此暂停点之前的日志、写库或外部调用可能再次发生。副作用应移到批准后的独立节点，或使用幂等键；同时不能在同一节点中随意重排多个 interrupt。
- **通俗理解**：`interrupt` 像流程走到付款前先存档并等待主管签字，签完后凭同一个任务编号继续。恢复时这一小段流程会从头再走，所以签字前不能放一个可能重复扣款的动作。

## 9. LLM 推理中的 KV Cache 是什么？它为什么能加速生成却会消耗大量显存？

- **分类**：LLM 基础与性能
- **难度**：中高级
- **考察要点**：自回归解码、Key/Value 复用、显存增长、缓存策略
- **参考答案**：
  - 自回归模型每次生成一个新 Token，都要让新 Query 与此前 Token 的 Key/Value 做注意力计算。KV Cache 保存历史 Token 各层的 Key/Value，后续步骤直接复用，避免反复计算整个前缀。
  - 缓存通常随层数、序列长度、批大小和 KV Head 数增长，长上下文与高并发时可能成为显存瓶颈。它减少的是重复计算，不会消除新 Token 对历史缓存的读取和注意力开销。
  - Dynamic Cache 灵活增长，Static Cache 便于编译优化但可能浪费预分配空间；显存不足时可选择滑动窗口、量化或 CPU Offload，但通常要在吞吐、延迟和精度之间权衡。
- **通俗理解**：KV Cache 像把读过章节的笔记留在桌上，写下一句时不用重新读整本书。对话越长、同时服务的人越多，桌上的笔记就越占地方，所以速度和显存必须一起权衡。

## 10. GraphRAG 与普通向量 RAG 有什么区别？什么时候值得使用？

- **分类**：RAG 架构
- **难度**：高级
- **考察要点**：实体关系、社区摘要、局部与全局查询、建设成本
- **参考答案**：
  - 普通向量 RAG 主要按文本语义相似度召回 Chunk；GraphRAG 还从语料提取实体、关系和关键声明，构建知识图谱与社区层级，并生成社区摘要供查询使用。
  - GraphRAG 的 Local Search 适合围绕特定实体及邻居寻找关系，Global Search 利用社区摘要回答跨文档的整体性问题。它更适合需要多跳关系、跨材料综合和全局主题分析的场景。
  - 图谱抽取、消歧、社区构建和摘要会显著增加索引成本，错误关系还可能传播到答案。简单 FAQ、精确事实查询或小语料通常先使用向量或混合检索，只有基准评测证明关系感知检索有收益时再引入 GraphRAG。
- **通俗理解**：普通 RAG 像按内容相似度找几段文字，GraphRAG 还会画出人物、组织和事件之间的关系网。只有问题需要顺着关系网“串线索”或总结全局时，这笔额外建设成本才更可能值得。
